Claude Code 2.1.136 → 2.1.138 — three patches in one Saturday ⚡

Update Workflow May 9, 2026 Δ vs 2.1.132 covered Issue #40

Headline deltas vs the 2.1.132 baseline:

  • Hard deny auto mode rules — block actions unconditionally regardless of classifier output. Direct relevance: dc's automated briefings tasks run in Auto mode; this lets the harness draw a hard line around destructive git operations (force push, branch -D) without relying on the classifier to refuse them.

⚡ Implication: Update to 2.1.138 today before kicking off Monday's runs. Specifically wire hard-deny rules into the briefings-site Claude Code config to block git push --force, git reset --hard, and rm -rf at the harness layer — Auto mode currently relies on classifier judgment for these and this gives you a deterministic gate. The MCP-after-/clear fix is the one that quietly matters most: any briefing run that compacts context mid-flight was at risk of losing its MCP servers silently.

§08 — Technicals

No fresh hardware or architecture announcements this weekend — the most interesting technical signal is the quiet maturation of MCP webhooks as the standard integration surface for agent pipelines, which is more architecturally significant than another GPU benchmark.

MCP webhooks as the agent-pipeline glue layer — a structural shift, not a feature drop ⚡

Update Workflow

Until last week, integrating an LLM agent into a CI/CD or batch pipeline meant polling: kick off the agent, then check periodically for completion. Webhooks invert this — the agent calls you on state change. Anthropic shipped this on May 6 for Managed Agents; OpenAI's Agents SDK has had it since March; LangGraph has had it via LangSmith since v1.0. The convergence means we now have a de-facto standard: agent runtimes emit webhooks on session-start / step-completion / session-end / failure, and orchestration systems consume them.

⚡ Implication: The "how do I integrate AI agents into my existing infra" question now has a stable answer. Designing new agent pipelines around webhooks (not polling, not "wait for tool to complete and return synchronously") is the architecturally-correct choice for any pipeline that runs longer than ~30 seconds. Direct application: dc's briefings-site multi-agent spike should be webhook-driven from day one.

🔬 Plain-English Explainer — Why webhooks vs polling actually matters

Imagine you order a coffee. Polling is when you keep walking back to the counter every 30 seconds asking "is it done yet?" — wasteful, and the more orders the shop has, the more you slow them down. Webhooks is the barista calling out your name when it's ready. You stay at your seat, the barista doesn't get interrupted, and the shop scales much further before things break.

For AI agents, this matters because a single "do my work" request can take minutes (the agent reads files, calls APIs, writes things). If your software is polling every few seconds to check whether the agent finished, you're wasting compute on both sides AND making the system harder to scale. Webhooks let the agent run as long as it needs and ping your system once when it's done — same way Stripe pings your server when a payment clears, instead of you constantly asking "did the payment go through yet?"

The practical result: agent pipelines built on webhooks scale further, fail more cleanly, and integrate into existing infrastructure (GitHub Actions, Slack alerts, Telegram bots) without bespoke wiring. For dc, this is the difference between "the briefings cron sometimes hangs at 5am" and "the briefings cron either succeeds or sends me a clean failure notification."
