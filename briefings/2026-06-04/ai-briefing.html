CadenceSWE-bench

After five frontier launches in nine days through late May, the first four days of June produced no new closed-model release. The SWE-bench Verified leaderboard is static at the top: Claude Mythos Preview 93.9%, Claude Opus 4.8 88.6%, Opus 4.7 (Adaptive) 87.6% (llm-stats / BenchLM, board refreshed 2 June, 92 models tracked). ⚡ So what: the version-number game is on pause — nothing in the top three changed your default this week. A quiet model board is the tell that the marginal capability gain is now coming from open weights catching up, not a new closed tier. That is this issue's thesis, and it lives in §04.

The frontier that moved is open, not closed — MiniMax M3 and DeepSeek V4 close the coding gap

Open weightsCoding

The week's only frontier-adjacent capability shift came from open-weight labs: MiniMax M3 (1 June, detailed in §04) claims to beat GPT-5.5 on SWE-bench Pro, and DeepSeek V4 (1.6T-parameter MoE, 49B active, 1M context) sits #1 on LiveCodeBench at 93.5 across all evaluated models, closed APIs included. Treat the specific scores as directional until independently reproduced — but the direction is unambiguous.

So what: for the first time the open coding frontier is close enough that a self-hostable model is a live option for cost-sensitive agent loops. The decision input changes from "is open good enough" to "is the inference-economics delta worth losing Opus-tier honesty and tool-use." Not yet for production agents; close enough to pilot.

§02 · Claude Ecosystem

Opus 4.8 stays the default; the live action is Claude Code v2.1.160–161 (2–3 June) tightening parallel-agent execution and write safety — and the Sonnet 4 / Opus 4 retirement is now 11 days out.

Claude Code v2.1.161 — parallel tool calls no longer kill their batch-mates ⚡

Claude Codev2.1.160–161

Two releases landed: v2.1.161 (3 June) and v2.1.160 (2 June). The change that matters for an agent-heavy workflow: parallel tool calls "no longer cancel other calls in the same batch." Previously a single slow or failing call could abort its siblings dispatched in the same turn — which silently truncated multi-agent fan-outs and Dynamic Workflow batches. Also in 2.1.161: OTEL resource labels for custom metric dimensions, and /mcp now collapses claude.ai connectors you've never signed into (less noise in long tool lists). v2.1.160 added a confirmation prompt before writing to shell startup files (.zshenv, .bash_login) and build-tool configs (.npmrc, .bazelrc, .pre-commit-config.yaml) — a supply-chain guard so a malicious clone can't get code execution through acceptEdits.

⚡ So what: the batch-cancel fix is a correctness patch, not a cosmetic one — if your fan-outs were occasionally returning fewer results than agents dispatched, this was likely why. Update. And if you ever run Claude Code on an untrusted repo, the write-prompt is a real defense, not a nag.

The deprecation wall is 11 days out — Sonnet 4 and Opus 4 retire 15 June ⚡

DeprecationMigration

Confirmed against the model-deprecations page: claude-sonnet-4-20250514 and claude-opus-4-20250514 both retire on the Claude API 15 June 2026 — requests after that date fail. Replacements are claude-sonnet-4-6 and claude-opus-4-8. That is the only Claude-side action with a hard deadline this fortnight. A separate, quieter trap to check while you're in there: temperature, top_p and top_k now return a 400 error when set to a non-default value on Opus 4.7 and later (including 4.8) — old code that passes a custom temperature will break even on a current model.

One-liner to run before 15 June

Grep your repos and dotfiles for the dated IDs that stop working: rg -n "claude-(sonnet|opus)-4-20250514". Anything it returns is a call that will start erroring in 11 days. While you're there, strip any hard-coded temperature/top_p/top_k on Opus-4.7-and-later calls.

§04 · Open-Source Pulse

MiniMax M3 (1 June) is the headline: the first open-weight model to combine frontier coding, a 1M-token context and native multimodality — and a sparse-attention architecture that claims a 15.6× decode speedup at million-token contexts.

MiniMax M3 — open-weight, MSA architecture
SWE-bench Pro 59.0% Terminal-Bench 2.1 66.0% MCP Atlas 74.2% OSWorld-Verified 70.06% 1M context native multimodal

MiniMax M3 — first open model to fold frontier coding, 1M context and multimodality into one stack

Open weightsMSA

Released 1 June, M3 is built on MiniMax Sparse Attention (MSA), which the lab reports delivers 15.6× faster decoding and 9.7× faster prefill versus the previous M2 generation at million-token contexts — the architectural unlock that makes a 1M window economically usable rather than a spec-sheet number. Self-reported benchmarks put it at 59.0% SWE-bench Pro (ahead of GPT-5.5 and Gemini 3.1 Pro), 66.0% Terminal-Bench 2.1, 74.2% MCP Atlas, 70.06% OSWorld-Verified, with text/image/video input and computer-use. Weights and the tech report are committed within ~10 days of launch (so ~11 June).

Verification note: at least one outlet has flagged the M3 benchmarks as vendor self-reported and not yet independently reproduced. Anchor to "claims to beat GPT-5.5 on SWE-bench Pro," not "beats." The number to wait for is a third-party SWE-bench Pro run after the weights drop.
So what: the open-weight gap to closed coding models is now measured in single benchmark points, not tiers. The MSA speedup is the more durable story than any one score — sparse attention that actually holds quality at 1M tokens is what makes long-context agents cheap. Watch the ~11 June weight release; that is when the claims become falsifiable.

EU AI Act — the overhaul is provisional; the 2 August transparency clock is not ⚡

EU AI ActAdoption

So what: for anyone shipping AI features into the EU, the planning assumption can't be "it got pushed back" until the formal vote lands. §06 · Workflow & Tools

The most useful shipped change this week is the Claude Code parallel-batch fix (§02); the broader workflow story is that agent reliability is now a tooling-and-research problem, not a model-capability one.

The batch-cancel fix is the practical workflow win — and it points at the real bottleneck

AgentsReliability

The headline tool change (detailed in §02) is Claude Code v2.1.161 ensuring parallel tool calls no longer cancel their batch-mates. It's small in the changelog and large in practice: as workflows fan out to tens-to-hundreds of subagents via Dynamic Workflows, a batch that silently drops siblings is the difference between "comprehensive" and "looks comprehensive." The fix matters because the failure was invisible.

Try this today

If you run multi-agent fan-outs, update to v2.1.161 and re-run a job you previously thought was flaky — the "occasionally returns fewer results than agents I dispatched" symptom is exactly what this patch addresses. Pair it with /usage's per-category breakdown (added in 2.1.149) to confirm every dispatched agent actually billed and returned.

Agent reliability is migrating from the model to the harness

ContextHarness

The through-line connecting this week's tool fix and the research below: the marginal gain in agent quality is increasingly about context management and execution plumbing, not raw model IQ. The same week a frontier launch didn't happen, the shipped wins were a batch-execution fix and a write-safety prompt — both harness, not model. That's the durable trend to internalise.

§07 · Research Radar

Two papers worth tracking, both attacking the long-horizon agent problem from opposite ends: one says manage context actively, the other says your RL reasoning gains were a sparse correction you could have gotten for free.

ARC — active, reflection-driven context management beats passive compression

arXivAgents

ARC: Active and Reflection-driven Context Management for Long-Horizon Information-Seeking Agents. The paper reframes context management as an active process — the agent treats its working context as a dynamic reasoning state and reorganises it when it detects degradation or misalignment, rather than passively summarising. Reported result: up to +11% absolute accuracy on BrowseComp-ZH versus passive compression baselines. Directly relevant to anyone running long agent loops where the model "forgets" mid-task.

Rethinking RL for LLM reasoning — the gain may be a sparse correction, not training

arXivReasoning

Rethinking RL for LLM Reasoning (REASONMAXXER, arXiv 2605.06241, early May). The provocative claim: RL's useful effect on math reasoning is a sparse, predictable correction that can be reproduced without RL at all — the model already knows the right reasoning paths and only needs to commit to the correct branch at a few critical moments. If it holds, it reframes "reasoning improvement" as a policy-selection problem rather than a training-compute problem.

So what: these are research signals, not products — but both point the same way as §06. The cheap wins in 2026 agents are looking less like "train a better model" and more like "manage the model's context and decision points better." Worth tracking which lab operationalises this first.
