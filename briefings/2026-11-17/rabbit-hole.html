The Orbiter That Died Because One File Said Pounds, Not Newtons

How a 1999 Mars spacecraft was lost to a single unit mismatch, a factor of 4.45, and why the error survived every check.

A NASA spacecraft worth about $125 million was lost at Mars in 1999 because one ground software file reported rocket thrust in pound-force seconds when the navigation software expected newtons. The gap is a factor of 4.45, and it took the orbiter from a planned 226 km flyby to roughly 57 km, low enough that it was probably destroyed in the upper atmosphere.

TL;DR

On 23 September 1999, NASA's Mars Climate Orbiter reached the planet and was never seen again. The cause was not a rocket failure or a hardware fault. One ground software file reported thruster impulse in pound-force seconds when the specification demanded newton-seconds. Every nudge the navigators modelled was therefore undercounted by a factor of 4.45, and the spacecraft arrived about 170 km lower than planned. The flight software was correct. Both sides of the interface were internally consistent, and the error sat exactly on the boundary between them.

Section 01

The Story

The Mars Climate Orbiter was meant to be a quiet workhorse. It was launched in 1998 to study the Martian climate and to relay communications for the Polar Lander that followed it. Its approach was planned with great care. A final trajectory correction was designed to place it at a closest approach of about 226 km above the surface, a safe margin for a controlled insertion into orbit. Then, as the spacecraft neared Mars, the navigation numbers stopped making sense. The arrival was not a gentle orbit insertion. The reconstructed low point was about 57 km, far below the 80 km the mission team regarded as the minimum survivable altitude.

The spacecraft had not malfunctioned. Its reaction wheels were building up angular momentum from sunlight pressing on the solar arrays, so small thrusters had to fire periodically to shed it. Each firing was logged as an impulse bit, the force multiplied by the time it acted. Those figures were not read directly from the spacecraft by the navigators. They came from a ground software file called Small Forces, which fed a table the trajectory team used to model every correction.

The file at the centre of it

Small Forces was a ground-side file generated by software that turned thruster telemetry into a table of impulses. The interface specification demanded newton-seconds. The file arrived in pound-force seconds, a unit in which the same number describes a force about 4.45 times smaller. The navigators' model therefore believed the thrusters had pushed less than they really had, and the trajectory they predicted drifted away from the real one with every firing.

The investigators were blunt about the origin. In the Phase I report, the board named the cause in a single line that has since become the standard citation for this failure:

the failure to use metric units in the coding of a ground software file
— NASA Mishap Investigation Board, Phase I Report, 1999

The board did not stop there. It also listed eight contributing causes that spanned software validation, staffing, training, communication and operations. The unit error was the spark, but the missing checks were the fuel. The mission was lost in a way that looked, from the inside, like an ordinary navigation problem until the numbers were audited against each other.

Section 02

The Mechanism

The physics is simple. Impulse is force integrated over time, and it has to be expressed in a consistent system of units. A newton-second and a pound-force second both measure impulse, and both are legitimate. One pound-force is about 4.45 newtons, so a figure of 1 in the wrong unit is read as 4.45 in the right one, or the reverse. When the ground file reported thruster impulse in the imperial unit, every downstream calculation that assumed metric units treated each firing as if it were weaker than it was. The error was systematic rather than random, which is why it accumulated across successive firings instead of averaging out.

This is also why the error was so hard to spot from inside any single team. The flight software on the spacecraft used metric units and was correct. The ground software that produced the file had been written to the imperial convention. The navigation software expected the metric one and was also internally consistent. Each program would pass a code review in isolation. The failure lived only in the interface, where one team's correct output became another team's wrong input. A number with no unit attached carries no warning that it is wrong.

Why the magnitude matters

Because the thruster effects were small and the spacecraft was spending months in a long approach, a systematic underestimate of thrust would look like a modest navigation residual rather than a catastrophe. Post-loss reconstruction using corrected values put the initial periapsis near 57 km, against a target of 226 km and a survivability threshold near 80 km. The numbers are reconstructions, not direct measurements, so the exact altitude is an estimate. The direction and rough scale of the error are not in doubt.

The fix is conceptually plain. Interfaces need to carry their units explicitly, and the software on both sides should reject a value whose unit does not match the contract. Typed quantities do this in modern engineering practice, but in 1999 the file was effectively a text table, and the contract was a document rather than a compiler check. The board's recommendations centred on verifying consistent unit use across both the spacecraft and the ground systems, which is a verification fix more than a coding fix.

Section 03

The Connections

The cockpit precedent. Aviation learned this lesson earlier and more painfully. In 1983 an Air Canada Boeing 767 was fuelled in pounds when the crew expected kilograms, and it ran dangerously short of fuel mid-flight before gliding to a safe landing at Gimli, Manitoba. The Mars orbiter is the same class of error at a different scale: a valid number in one system read as a valid number in another. The difference is that the 767 crew could see the fuel gauges, whereas the navigators were looking at a trajectory model that quietly agreed with itself.

Why the obvious explanation falls short. The easy story is that a careless programmer made a mistake. The board's own framing pushes against that. Its findings describe a project in which the navigation team was under-staffed, the verification process failed to catch an error that a simple reasonableness check might have flagged, and the communication between groups was thin. Blaming one coder treats a systems failure as a personal one, and it guarantees the next project repeats the pattern with a different coder and the same unlabelled number.

The companion loss and a coda. The orbiter was not the only casualty of that season. Contact with the Mars Polar Lander ended on 3 December 1999, a little over two months after the orbiter was lost, and the two losses are often told together as a single lesson about the cost of thin margins. There is an irony in the physics as well. The error was a factor of 4.45, a number that is a fixed conversion between two honest systems of measurement. Nothing about the physics was wrong, and both teams had done solid work. The mistake was a label that was missing from one number and assumed by another.

The live parallel in markets and AI. Any pipeline that passes bare numbers between components has the same exposure. A trading system that reads a price in cents while its risk engine expects dollars, or a basis-point figure that arrives where a percentage was expected, can misstate exposure by an order of magnitude with every individual check passing. Agentic AI tools are a current example, since tool outputs are often returned as plain text and consumed by a model that has no reliable way to know the unit. This is my own analogy rather than a documented finding in either field, but the Mars case is the clearest published warning that the unit is part of the data, not decoration on it.

📄
The Phase I report itself

The NASA Mishap Investigation Board's first report is short, specific and readable. It shows how a root cause and a set of contributing causes can be separated cleanly, which is the skill most engineering post-mortems lack.

🛬
The Gimli Glider

The 1983 Air Canada landing at Gimli is the aviation twin of this story, a pounds-versus-kilograms error that ended with a glider landing and no deaths. Reading both side by side makes the pattern hard to unsee.

🔭
The Mars Polar Lander

The lander lost two months after the orbiter is the other half of the 1999 Mars story. Its failure has a different and still debated cause, which makes it a useful contrast for thinking about how missions fail.

📚
The Phase II report

The board's second report turns from the unit error to systems engineering, project management and verification. It is the document that explains why a single conversion factor could sit undetected through a whole mission.
