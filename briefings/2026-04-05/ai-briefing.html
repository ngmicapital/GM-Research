[Fundamentals]
What Is Mixture of Experts (MoE) — and Why It Shapes Every Major Model Release in 2026

Mixture of Experts (MoE) is an architectural pattern that lets a large neural network behave like a committee of specialists. Instead of running all of a model's parameters on every input — which is what "dense" models like GPT-4 or Llama 3 do — an MoE model divides its neural layers into discrete "expert" sub-networks and routes each token (roughly: each word fragment) to only 2–4 of those experts at a time. The rest of the network sits idle for that token.

The practical result: an MoE model with 200 billion total parameters might only activate 20–30 billion on any given token. That means the compute cost of a forward pass scales with activated parameters, not total parameters. Gemma 4's 26B MoE model activates just 4B parameters per forward pass — a 6.5× compute reduction while retaining the representational capacity of a 26B parameter bank. This is why MoE models consistently punch above their "active parameter" weight class on benchmarks.

The catch is routing. A "router" network must decide which experts to activate for each token, and it must do this in milliseconds. If the router is poorly trained, you get "expert collapse" — most tokens route to the same 2–3 experts, wasting the rest of the network. Training MoE well requires careful load-balancing losses and architectural attention to expert diversity. This is non-trivial, which is why MoE only became practically viable at scale after Google's Switch Transformer paper in 2021 and became mainstream with Mistral's Mixtral in 2023.

In 2026, every frontier lab is shipping MoE variants: Gemma 4 26B MoE, Grok 4.20, and reportedly GPT-5.5 "Spud." The trend signals that compute efficiency — not raw parameter count — is now the primary competitive lever. A model that achieves GPT-5.4 quality at 40% of the inference cost is not an equivalent product; it's a commercial disruption.

Why this matters for the AI landscape: MoE architecture breaks the direct link between "model quality" and "compute cost per query." This is deflationary for API pricing and inflationary for demand — cheaper inference enables applications that were previously cost-prohibitive. It also complicates benchmark comparisons: citing total parameter count as a capability metric is increasingly meaningless. What matters is activated parameters per token (inference cost) and training compute (capability ceiling). Keep this frame handy when evaluating Spud's inevitable claims at launch.

Research Radar
ThinkTwice shows that self-refinement adds 11.5 points to AIME performance — the implication is that iterative review loops, not just longer thinking chains, are the next capability lever.
[Research]
ThinkTwice — Self-Refinement Adds 11.5 Points on AIME After One Revision Pass

ThinkTwice is a new training and inference framework that improves model performance through structured self-refinement — the model generates a first answer, then explicitly reviews and revises that answer in a second pass. On Qwen3-4B, ThinkTwice outperforms competitive baselines on AIME by 5 points before refinement and by 11.5 points after one self-refinement step. The framework also improves performance on LiveCodeBench and GPQA Diamond. [arXiv preprint — independent replication pending]

Why this matters: the dominant assumption in scaling has been that "longer thinking chains" (more CoT tokens at inference time) produce better answers. ThinkTwice's result suggests a structured two-pass approach — think, then revise — is more efficient than a single long chain of the same total length. The insight is that models make systematic errors in first-pass reasoning that they can identify and correct if given a structured review prompt, but won't self-correct in a single continuous generation.

Why it matters in 6 months: if ThinkTwice's approach is validated and lab-adopted, expect to see "refinement passes" become a standard feature in model APIs — similar to how test-time compute scaling (o1-style) became mainstream. The practical form would be an API parameter that triggers one or more revision cycles automatically before returning the answer. This would improve reliability on exactly the tasks AI agents struggle with most: multi-step reasoning, code debugging, and structured analysis.

⚡ Implication: Monitor for code release and community replication. If ThinkTwice holds up, it represents a training-level fix for systematic first-pass reasoning errors. The version of this that matters for dc arrives when it's implemented in a production API endpoint — probably 6–9 months from now. No action today.
[Research] [Use Case]
AGENTS.md Files — Empirical Evidence That Documentation Changes AI Coding Agent Behaviour

"On the Impact of AGENTS.md Files on the Efficiency of AI Coding Agents" (arXiv 2601.20404) is an empirical study measuring how AI coding agents (including Claude Code-style tools) respond to structured project documentation placed in an AGENTS.md file at the repository root. The finding: agents with access to well-structured AGENTS.md documentation complete tasks with significantly fewer unnecessary tool calls, fewer hallucinated file paths, and higher first-pass success rates than agents without that documentation.

The mechanism: without documentation, AI agents must infer project structure, conventions, and constraints from code exploration — which takes token budget and generates errors on inferences that turn out to be wrong. AGENTS.md provides ground truth upfront, similar to how a senior engineer's onboarding briefing reduces a new hire's fumbling around in a new codebase.

The paper evaluates specific content patterns: agents benefit most from entries that describe testing commands, deployment steps, where to find configuration files, and which files/directories should not be modified. Narrative descriptions of architecture help less than concrete instructions.

⚡ Directly actionable for dc: Claude Code benefits from AGENTS.md (or CLAUDE.md, which you already use). If your CLAUDE.md primarily describes who you are rather than specific operational instructions (which files to avoid, which commands to run, which MCP tools are available), it's worth a review. The study suggests the most valuable entries are concrete operational facts, not context-setting prose.
