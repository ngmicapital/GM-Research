    🔧 Tool Use — From Brittle Routers to Native Intelligence


    *"Routers like those are basically guesses about the user intent written in conditional if statements. They're brittle, and they're sort of the first thing that breaks when you try adding a new tool."* (03:50)

    Old pattern:

    
# Heuristic router (fragile)
if "SQL" in user_message or "database" in user_message:
    tools = [database_tool]
elif "search" in user_message:
    tools = [search_tool]
else:
    tools = [default_tools]

    This breaks the moment a user says something the pattern doesn't anticipate.


    New pattern:

    
# Just give Claude everything
tools = all_tools
response = claude.messages.create(model="claude-opus-4-7", tools=tools, ...)

    Tool selection accuracy is now high enough that the router is a net negative. When a tool errors, Claude sees the error, recovers, and retries autonomously — no external retry decorator needed.


    💡 **Key Insight:** This is the architectural shift from the model-as-input/output-box to the model-as-agent. In the old paradigm, the developer had to manage tool orchestration. In the new paradigm, that orchestration is internal to the model. The API surface simplifies; the model complexity increases (invisibly to the developer).

    ⚡ Quick Tip: Include Output Schema in Tool Descriptions


    *"By telling Claude what a tool will return, Claude can plan ahead without a round trip."*

    
tools = [{
    "name": "search_docs",
    "description": """Search the documentation. 
    Returns: {id: string, title: string, snippet: string, score: float}.
    Use 'score' to rank results — higher is more relevant.""",
    "input_schema": {
        "type": "object",
        "properties": {"query": {"type": "string"}},
        "required": ["query"]
    }
}]

    Without the return schema: Claude calls the tool, gets results, then has to make a second inference about what to do with them.


    With the return schema: Claude already knows a score field will be returned, plans to sort by it, and executes that in one pass.


    Net effect: fewer round trips, more efficient context use, smarter tool chaining.


    ⚡ Claude Code Tip: Pre/Post Tool-Use Hooks


    In claude_settings.json (Claude Code):

    
{
  "hooks": {
    "before_tool_use": "my_validation_script.py",
    "after_tool_use": "my_logging_script.py"
  }
}

    Use cases:

  • **Block tool calls** in specific contexts (e.g., prevent file deletion in production paths)
  • **Log outputs** programmatically for audit trails
  • **Transform results** before they reach Claude's context


    • 🧠 Context Management — From Bespoke Pipelines to Config


    *"By offering 1 million context length at flat pricing, that already reduces most of the window pressure."* (07:40)

    Old pattern:

  • Custom chunking logic
  • RAG pipelines to retrieve relevant context
  • Summarization calls to a secondary model every N turns
  • Manual cache breakpoint management

    • New pattern:

  • 1M context window (flat pricing, no per-token penalty at short ranges)
  • Server-side compaction (Anthropic handles summarization automatically)
  • Context editing via API (programmatically prune what's in context)

    • The result collapses a 200-line scaffolding problem into a few lines of config.


    🔗 **Connection:** Server-side compaction + 1M context → the "infinite context window feeling" referenced in the morning keynote. The UX of infinite context (no context-management cognitive load) is now achievable without the engineering burden.

    ⚡ Quick Tip: Clear Tool Results Every End-Turn


    After each agent turn, prune stale tool outputs from context:

  • Screenshots → read, decision made → delete the screenshot
  • File reads → extracted information → delete the file content
  • Search results → relevant facts noted → delete the raw results

    • What to keep: The decision the model made based on those results (already in the transcript). The raw results themselves are context-expensive noise after the decision is made.


    Savings: Can be substantial. A single large file read or screenshot can consume tens of thousands of tokens. If the model has already processed it, retaining it wastes context on every subsequent turn.


    ⚡ Claude Code Tip: /context Command


    In Claude Code, type /context to get a live color-coded breakdown of what is consuming your context window:

  • Messages
  • Tool results
  • System prompt
  • MCP definitions

    • This makes abstract context pressure visceral and actionable. Optimization suggestions are included.



    💻 Code Execution — The Write-Run-Fix Loop Goes Internal


    *"That entire loop effectively happens inside a single API turn."* (10:45)

    Old pattern:

  • Developer finds a VM provider
  • Spins up sandbox
  • Model outputs code
  • Developer puts code on VM
  • VM runs code
  • Developer parses traceback
  • Feeds traceback back to model
  • Repeat until success

    • New pattern:

    Claude gets a hosted server-side sandbox automatically via the code execution tool. The write-run-fix loop runs internally, within a single API turn. No harness round trips.


    Mental model: Claude gets "its own little computer." Two environments:

  • **Code execution sandbox** — stateless compute, data analysis, custom library installs, doesn't touch your local filesystem
  • **Bash (local)** — your repo, your Python env, local context

    • Claude knows which to use when. The distinction is clean: sandbox for scratch work, local bash for context that only exists on your machine.


    ⚡ Claude Code Tip: /schedule Command


    Use /schedule in Claude Code to set cron-triggered autonomous runs. The self-iterating loop (write → run → test → fix) can now run on a timer, completely autonomously, while you sleep.



    🖥️ Computer Use — Coordinate Math Is Gone


    *"So you'd have to write all that code, and then wrap it in retries and verify statements as well."* (13:21)

    Old pattern for computer use:

  • Capture 1080p screenshot
  • Downscale to fit Claude's pixel limits (record the scale factor)
  • Claude samples a click coordinate in the downscaled image
  • Scale click back up to original resolution
  • Verify click landed correctly
  • Wrap in retries

    • New pattern:

  • Opus 4.7 accepts native resolution up to **1440p**
  • Returns **1-to-1 pixel coordinates**
  • No scale factor tracking
  • No rescaling code
  • Just send the image, trust the click

    • OS World benchmark: The headline computer use eval. Less than 12 months ago, Claude scored below 50% — it could not complete half of the tasks. As of the talk: 78% on Opus 4.7, approaching 80%. This is the "cusp of broad usability" in Lucas's framing.


    🌐 **Consensus Check:** OS World is a legitimate and widely-used computer use benchmark. The sub-50% → 78% trajectory in under 12 months is real and aligns with published SOTA results. For context, human performance on OS World is approximately 72–75% — meaning Claude is now at or above human-level on this benchmark.

    💡 **Key Insight:** Claude may now be better than the average human at computer use on OS World's task distribution. This is not a cherry-picked benchmark — it covers professional software (spreadsheets, word processors, IDEs) and consumer apps across Windows and macOS.

    ⚡ Quick Tip: Experiment Across Resolutions and Formats


    While native 1440p is supported:

  • Different use cases may benefit from different resolutions
  • JPEG, PNG, and WebP compress differently → different compression artifacts → different impact on click accuracy for specific UI types
  • Test your specific UI target across formats to find the optimum
  • Only downscale if above 1440p

    📐 The Strategic Frame — Where to Put Your Engineering Effort


    Lucas's closing argument is the most strategically important section of the talk:


    Half-life rule: Any code that compensates for model unreliability has a half-life of months. The model will absorb those compensations. Your retry logic, your router, your verification loop — Anthropic is actively working to make those unnecessary.


    What compounds instead:

  • Custom tools that connect the model to your specific world
  • Your proprietary data and context
  • Your auth and access layers
  • Your specific business logic

    • "The model can't absorb what it can't see." The code that connects Claude to your world is the code that compounds; the scaffolding code is the code that decays.


    The "agent front door" prediction: Lucas predicts that in the near future, every piece of software will have a front door for agents — an API surface or protocol specifically designed for agent access. The interesting engineering question is what you put on the other side of your front door that nobody else can.


    🧵 **Running Thesis:** The Anthropic internal thesis is that the API boundary is moving. Previously, the API was raw model I/O; now it includes orchestration, memory, tools, and execution environments. Future: the API boundary moves further out, absorbing more of the stack. Each time it does, the dev's job shifts from building scaffolding to building unique connectors. Status: **actively unfolding** — this talk describes it happening in real time.


    Phase 3: Protocol Cards


    🔧 Tool Definition Protocol — Input + Output Schema

    **One-Liner:** Don't just tell Claude what parameters a tool takes — tell it what the tool returns. This saves round trips and enables smarter planning.

    Before (input only):

    
"description": "Search the docs for relevant information."

    After (input + output):

    
"description": """Search the docs. Returns: {id, title, snippet, score}.
Use score to rank — higher is more relevant."""

    🧹 Context Pruning Protocol — Clear Stale Tool Results

    **One-Liner:** After each agent turn, programmatically remove screenshots, file reads, and search results that have already been processed. Keep only the decisions they informed.

    Implementation: Add a post-turn hook that deletes tool result content from the message array while preserving Claude's summary/reasoning about those results.
