🔧 Tool Use — From Brittle Routers to Native Intelligence

"Routers like those are basically guesses about the user intent written in conditional if statements. They're brittle, and they're sort of the first thing that breaks when you try adding a new tool." 03:50

Old pattern — heuristic router (fragile):

# Route by keyword guess
if "SQL" in user_message or "database" in user_message:
    tools = [database_tool]
elif "search" in user_message:
    tools = [search_tool]
else:
    tools = [default_tools]

This breaks the moment a user says something the pattern doesn't anticipate. A new tool requires editing the router; an unexpected synonym bypasses the right tool entirely.

New pattern — give Claude everything:

# Trust Claude's native tool selection
tools = all_tools
response = claude.messages.create(model="claude-opus-4-7", tools=tools, ...)

Tool selection accuracy is now high enough that the router is a net negative. When a tool errors, Claude sees the error, recovers, and retries autonomously — no external retry decorator needed.

💡 Key Insight This is the architectural shift from the model-as-input/output-box to the model-as-agent. In the old paradigm, the developer had to manage tool orchestration. In the new paradigm, that orchestration is internal to the model. The API surface simplifies; the model complexity increases (invisibly to the developer). The complexity didn't go away — it migrated.

⚡ Quick Tip: Include Output Schema in Tool Descriptions

"By telling Claude what a tool will return, Claude can plan ahead without a round trip."

Before (input only):

"description": "Search the documentation for relevant information."

After (input + output schema):

tools = [{
    "name": "search_docs",
    "description": """Search the documentation.
    Returns: {id: string, title: string, snippet: string, score: float}.
    Use 'score' to rank results — higher is more relevant.""",
    "input_schema": {
        "type": "object",
        "properties": {"query": {"type": "string"}},
        "required": ["query"]
    }
}]

Without the return schema: Claude calls the tool, gets results, then has to make a second inference about what to do with them — an extra round trip and extra tokens.

With the return schema: Claude already knows a score field will be returned, plans to sort by it, and executes that in one pass.

Net effect: fewer round trips, more efficient context use, smarter tool chaining. This is the highest-leverage single tip in the entire talk.

🧵 Running Thesis The API boundary is moving. Previously: raw model I/O. Now: orchestration, memory, tools, execution environments. Next: the boundary moves further out, absorbing more of the stack. Each time it does, the dev's job shifts from building scaffolding to building unique connectors. Status: actively unfolding — this talk describes it happening in real time.

⚡ Claude Code Tip: Pre/Post Tool-Use Hooks

In claude_settings.json:

{
  "hooks": {
    "before_tool_use": "my_validation_script.py",
    "after_tool_use": "my_logging_script.py"
  }
}

Use cases: block tool calls in specific contexts (e.g., prevent file deletion in production paths); log outputs programmatically for audit trails; transform results before they reach Claude's context.

🌐 Consensus Check The removal of pre-filtering routers is Anthropic's own recommendation, backed by their internal benchmarking. Community validation is emerging: developers who have removed routers in 2025 broadly report improved tool selection, especially for ambiguous user queries. The caveat for very large tool sets (100+ tools) remains active — context budget and latency may require selective pruning at that scale.

🧠 Context Management — From Bespoke Pipelines to Config

"By offering 1 million context length at flat pricing, that already reduces most of the window pressure." 07:40

Old pattern:

  • Custom chunking logic
  • RAG pipelines to retrieve relevant context
  • Summarization calls to a secondary model every N turns
  • Manual cache breakpoint management

This was a significant engineering project. 200+ lines of scaffolding, tight coupling between the chunking strategy and the model's context capacity, and a maintenance burden every time the context window changed.

New pattern:

  • 1M context window (flat pricing)
  • Server-side compaction (Anthropic handles summarization automatically)
  • Context editing via API (programmatically prune what's in context)

The result collapses a 200-line scaffolding problem into a few lines of config. The "infinite context window feeling" — no context-management cognitive load — is now achievable without the engineering burden.

💡 Key Insight Server-side compaction is strategically significant beyond convenience: it means the compaction strategy improves as Anthropic's models improve, without the developer doing anything. A custom summarization pipeline improves only when the developer invests time. The compaction moat is now with Anthropic, not the developer.

⚡ Quick Tip: Clear Stale Tool Results Every End-Turn

After each agent turn, prune stale tool outputs from context:

  • Screenshots → read, decision made → delete the screenshot
  • File reads → extracted information → delete the file content
  • Search results → relevant facts noted → delete the raw results

What to keep: The decision the model made based on those results (already in the transcript). The raw results themselves are context-expensive noise after the decision is made.

Savings: Can be substantial. A single large file read or screenshot can consume tens of thousands of tokens. If the model has already processed it, retaining it wastes context on every subsequent turn.

⚡ Claude Code Tip: /context Command

In Claude Code, type /context to get a live colour-coded breakdown of what is consuming your context window: messages, tool results, system prompt, MCP definitions. This makes abstract context pressure visceral and actionable. Optimization suggestions are included.

🔍 Source Verified ✅ 1M context window claim confirmed. Anthropic's Claude 3.5 and Claude 4 series feature up to 200K context as standard, with 1M available for select API tiers. Server-side compaction was introduced as an API feature in early 2025. Context editing (programmatic pruning of the messages array) is documented in the Anthropic API reference. All three features are live and verifiable.

💻 Code Execution — The Write-Run-Fix Loop Goes Internal

"That entire loop effectively happens inside a single API turn." 10:45

Old pattern:

  1. Developer finds a VM provider
  2. Spins up sandbox
  3. Model outputs code
  4. Developer puts code on VM
  5. VM runs code
  6. Developer parses traceback
  7. Feeds traceback back to model
  8. Repeat until success

New pattern: Claude gets a hosted server-side sandbox automatically via the code execution tool. The write-run-fix loop runs internally, within a single API turn. No harness round trips.

Mental model: Claude gets "its own little computer." Two environments:

  • Code execution sandbox — stateless compute, data analysis, custom library installs, doesn't touch your local filesystem
  • Bash (local) — your repo, your Python env, local context

Claude knows which to use when. The distinction is clean: sandbox for scratch work, local bash for context that only exists on your machine.

📜 Analog The shift from the multi-step "hand the code to a VM" loop to the internal write-run-fix loop mirrors the transition from batch computing to interactive computing in the 1960s–70s. The same compaction of the feedback loop that made computers accessible to individuals now makes agentic code execution accessible to applications. Each compression of the feedback loop unlocks an order of magnitude more use cases.

⚡ Claude Code Tip: /schedule Command

Use /schedule in Claude Code to set cron-triggered autonomous runs. The self-iterating loop (write → run → test → fix) can now run on a timer, completely autonomously, while you sleep. This is the first version of always-on autonomous software development.

🖥️ Computer Use — Coordinate Math Is Gone

"So you'd have to write all that code, and then wrap it in retries and verify statements as well." 13:21

Old pattern for computer use:

  1. Capture 1080p screenshot
  2. Downscale to fit Claude's pixel limits (record the scale factor)
  3. Claude samples a click coordinate in the downscaled image
  4. Scale click back up to original resolution
  5. Verify click landed correctly
  6. Wrap in retries

New pattern:

  • Opus 4.7 accepts native resolution up to 1440p
  • Returns 1-to-1 pixel coordinates
  • No scale factor tracking
  • No rescaling code
  • Just send the image, trust the click

OS World benchmark: The headline computer use eval. Less than 12 months ago, Claude scored below 50% — it could not complete half of the tasks. As of the talk: 78% on Opus 4.7. This is the "cusp of broad usability" in Lucas's framing.

🌐 Consensus Check OS World is a legitimate and widely-used computer use benchmark. The sub-50% → 78% trajectory in under 12 months is real and aligns with published SOTA results. For context, human performance on OS World is approximately 72–75% — meaning Claude is now at or above human-level on this benchmark. The benchmark covers professional software (spreadsheets, word processors, IDEs) and consumer apps across Windows and macOS — not cherry-picked tasks.
💡 Key Insight Claude may now be better than the average human at computer use on OS World's task distribution. This is not framed as a headline by Lucas — it's mentioned in passing. The practical implication: any workflow a human can do by looking at a screen and clicking, Claude can now perform at or above human accuracy. The bottleneck is no longer capability; it is integration and trust.

⚡ Quick Tip: Experiment Across Resolutions and Formats

While native 1440p is supported:

  • Different use cases may benefit from different resolutions
  • JPEG, PNG, and WebP compress differently → different compression artifacts → different impact on click accuracy for specific UI types
  • Test your specific UI target across formats to find the optimum
  • Only downscale if above 1440p

⚡ Claude Code Tip: Claude in Chrome Integration

With Claude in Chrome installed (claude.ai/chrome), Claude Code can: launch and control your Chrome browser; navigate the web within its coding session; test local development servers; perform browser-based QA automatically.

Demo highlight: Claude Code working on a project management dashboard with two bugs (card creation broken, drag-and-drop landing in wrong column). Claude opened Chrome itself, reproduced the bug, diagnosed it by reading the DOM, fixed the code, and retested — without the developer touching anything.

🔗 Connection The computer use + Claude in Chrome demo is the first fully agentic QA loop shown at an Anthropic conference. It parallels Karpathy's argument (in his Sequoia talk) that "agent-native infrastructure" is the future requirement. Here Anthropic shows the inverse: existing human-native software can be tested by agents as-is, without requiring software to be rewritten for agents. The two paths converge — rewrite for agents, or let agents meet human software where it is.

📐 The Strategic Frame — Where to Put Your Engineering Effort

Lucas's closing argument is the most strategically important section of the talk:

Half-life rule: Any code that compensates for model unreliability has a half-life of months. The model will absorb those compensations. Your retry logic, your router, your verification loop — Anthropic is actively working to make those unnecessary.

What compounds instead:

  • Custom tools that connect the model to your specific world
  • Your proprietary data and context
  • Your auth and access layers
  • Your specific business logic
"The model can't absorb what it can't see." 20:27

The code that connects Claude to your world is the code that compounds; the scaffolding code is the code that decays.

The "agent front door" prediction: Lucas predicts that in the near future, every piece of software will have a front door for agents — an API surface or protocol specifically designed for agent access. The interesting engineering question is what you put on the other side of your front door that nobody else can.

🎯 Against Consensus The half-life framing is more aggressive than most AI engineering advice. The mainstream view is to build defensive scaffolding and upgrade as models improve. Lucas's view is that building scaffolding at all is misdirected effort — the model is going to absorb it in months, and time spent on scaffolding is time not spent on connectors. This is a minority position in practice, though directionally correct based on 2023–2025 history.

🧹 Context Pruning Protocol — Clear Stale Tool Results

After each agent turn, programmatically remove screenshots, file reads, and search results that have already been processed. Keep only the decisions they informed.

Implementation:

Add a post-turn hook that deletes tool result content from the message array while preserving Claude's summary/reasoning about those results. A single large file read can consume tens of thousands of tokens; once processed, it should not persist.
