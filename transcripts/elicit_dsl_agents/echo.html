⚡ Echo — Trustworthy Agents via Custom DSL: The Elicit Architecture

James Brady · Elicit·Code with Claude Conference 2026·May 2026

Core insight: Identical outputs can be produced by fundamentally different mechanisms — and those mechanisms determine whether you should trust the output. Elicit's response: build a custom Turing-incomplete DSL as the interface between planning (LLM) and execution (deterministic interpreter). The mechanism becomes inspectable, verifiable, and auditable. Speed vs rigor is an explicit design choice encoded in the language itself, not an emergent property of prompting.

The Architecture

  • Planner: LLM receives user request → outputs a plan in Elicit's custom DSL (Turing-incomplete)
  • Interpreter: Deterministic component reads the DSL plan → executes concrete tasks
  • Executor quiver: Pool of models selected per task — different models for different task types
💡 Why Turing-Incomplete

A Turing-complete language can express any computation, including infinite loops and unbounded resource usage. Turing-incomplete languages can't. By designing the DSL to be Turing-incomplete, Elicit guarantees that any valid plan terminates. This is a formal safety property, not a best-effort one.

Trust Through Mechanism

The provocative opener: if two systems produce identical output, you don't trust them equally — you trust the one whose mechanism you understand and whose process is more rigorous. The DSL makes the mechanism inspectable: you can read the plan before execution, audit what happened after, and formally verify certain properties of the plan structure.

Speed vs Rigor as Design Choice

Elicit's DSL encodes the speed/rigor tradeoff explicitly. High-rigor plans use more model calls, more critique-and-redrafting, more verification steps. High-speed plans use fewer, cheaper operations. The user's task and domain determine where on this spectrum to operate — and that's now a visible, adjustable parameter rather than an implicit consequence of prompting.

Architectural Values → Language Design

💡 Key Principle

The design of Elicit's DSL is described as "concrete instantiations of company values." Verifiability, transparency, and rigor aren't aspirational principles — they're properties encoded in the language grammar. This is the right way to think about architectural decisions: they should reflect and enforce your values, not just try to achieve them through prompting.

When to Consider a Custom DSL

⚠ High Investment

Building a DSL is a significant engineering investment. It's appropriate for: domains requiring formal auditability (research, legal, medical), systems where the planning-execution interface needs to be versioned and maintained, and teams with enough volume to justify the upfront cost. For most teams, structured outputs or function calling are sufficient.

Actions

  1. For any agent with an auditing requirement: consider separating planning (LLM → structured plan) from execution (deterministic interpreter)
  2. Evaluate whether your current tool-calling architecture makes the mechanism inspectable — can you audit what the agent planned before it executed?
  3. Consider using structured output schemas as a lightweight DSL — you get some of the inspectability benefits without building a full language
  4. For high-stakes domains: document your speed/rigor tradeoffs explicitly rather than letting them emerge from prompting
