Trustworthy Agents via Custom DSL: The Elicit Architecture

James Brady · Elicit·Code with Claude Conference 2026·May 2026 DSLTrustworthy AIAgent Design

Core argument: The mechanism by which an agent produces an output is as important as the output itself. Elicit's answer to this problem: a custom Turing-incomplete domain-specific language (DSL) that separates planning (LLM → structured plan) from execution (deterministic interpreter → concrete tasks). The mechanism becomes inspectable, the plan becomes auditable, and the speed/rigor tradeoff becomes an explicit design choice rather than an emergent property of prompting.

The Mechanism Matters

Brady opens with a deceptively simple question: if two systems produce identical output, do you trust them equally? The answer is clearly no — but why?

The trust difference comes from the mechanism. A static analysis tool powered by an older, smaller model that says "no security vulnerabilities" is a fundamentally different object than one powered by the latest model with tool use, critique, and redrafting — even if both produce the same verdict.

The implication: how an answer is produced matters, not just what the answer is. For high-stakes domains — research, legal analysis, security assessment — users need to trust and inspect the mechanism, not just accept the output.

📡 The Auditability Problem

With standard LLM agents, the reasoning process is opaque. You see inputs and outputs, but the intermediate steps — what the model considered, what it rejected, how it decomposed the task — are inaccessible. For regulated industries or high-stakes decisions, this is a blocker.

The DSL Architecture

Elicit's solution is a three-component system:

1. The Planner (LLM → DSL Plan)

The planner receives a user's research request and outputs a structured plan written in Elicit's custom DSL. The plan describes what steps to take, in what order, with what resources. It does not execute anything — it is a declarative description of the intended process.

2. The Interpreter (Plan → Execution)

A deterministic interpreter reads the DSL plan and executes it. Deterministic means: given the same plan, the interpreter always takes the same actions. No LLM involved in this step — execution is fully predictable and auditable.

3. The Executor Quiver (Task → Model Selection)

Concrete tasks from the interpreter are dispatched to a pool of models — the "quiver." Different task types route to different models: fast and cheap for simple extraction, powerful and slow for complex synthesis. The quiver is configurable and can be updated without changing the planner or interpreter.

💡 Separation of Concerns

This architecture cleanly separates planning (what to do), execution (how to do it), and task performance (which model to use). Each layer can be improved, versioned, and audited independently. This is classic software engineering applied to LLM systems.

Turing-Incomplete by Design

The DSL is deliberately Turing-incomplete. This is a non-obvious choice that deserves explanation.

A Turing-complete language can express any computation — including infinite loops. Elicit chose Turing-incompleteness to guarantee that any valid plan will terminate in finite time. This is a formal property: you can prove termination for any program in the language.

The practical implications:

  • No infinite loops — the interpreter can always determine a plan will complete
  • Bounded resource usage — you can upper-bound compute cost per plan
  • Formal verification becomes tractable — certain properties can be checked mechanically
  • Simpler interpreter — no need to handle non-terminating programs
🔁 Analog: Regular Expressions

Regular expressions are Turing-incomplete — they can't match all possible patterns, but everything they match is guaranteed to complete in polynomial time. This limitation is a feature: you get predictability and formal analysis. Elicit's DSL makes the same tradeoff for agent planning.

Speed vs Rigor: An Explicit Design Choice

Every agent system implicitly makes speed/rigor tradeoffs — how many model calls, how much critique-and-redrafting, how much verification. In standard prompting-based systems, these tradeoffs are implicit, embedded in the prompt, and hard to adjust.

Elicit's DSL makes them explicit. The language provides constructs for different levels of rigor: fast-path operations that use fewer calls, high-rigor paths that add verification steps and critiques. The planner chooses where on this spectrum to operate based on the task and domain.

Brady describes this as a genuine design choice rather than a universal best practice: the right level of rigor depends on the task (fast literature scan vs. rigorous systematic review), the domain (consumer research vs. clinical trial evidence), and the user (expert researcher vs. first-time user).

💡 Making Implicit Explicit

The value of encoding speed/rigor tradeoffs in the DSL isn't that it automatically makes the right choice — it's that it makes the choice visible and adjustable. Previously a prompt engineering detail, now a first-class parameter that can be versioned, compared, and explained to users.

Architectural Values → Language Design

Brady makes an interesting claim: "the architectural choices [in the DSL] are concrete instantiations of company values." Elicit's core values — verifiability, transparency, rigorous research — are embedded in the language design:

  • Verifiability: Turing-incomplete → formal termination guarantees; deterministic interpreter → auditable execution
  • Transparency: Plans are human-readable DSL, not opaque LLM reasoning; users can see what the agent planned before it ran
  • Rigor: Explicit rigor constructs in the language; speed/rigor tradeoff is visible rather than implicit

This framing — architecture as instantiated values — is more useful than treating architectural choices as purely technical decisions. It explains why you made a choice (because of this value we hold) rather than just what you chose.

Applicability and Limits

Building a custom DSL is not appropriate for most teams. The engineering investment is substantial: language design, parser, interpreter, tooling, documentation. Brady's audience is primarily teams with high auditability requirements and enough scale to justify the investment.

However, the underlying principle — separating planning (structured) from execution (deterministic) — is applicable at lower cost:

  • Structured outputs: Having the LLM output a structured plan (JSON schema) before executing is a lightweight version of the DSL approach
  • Function calling with confirmation: Show the user the planned function calls before executing — cheap approximation of plan inspection
  • Step-by-step logging: Log each interpreter step for post-hoc auditability
⚠ When NOT to Build a DSL

Don't build a DSL if: your task variety is high (the language scope explodes), your team lacks PL engineering experience, your volume is low (ROI won't be there), or your domain doesn't require formal auditability. Standard function calling + structured outputs cover most cases.

Implications

📡 Research-Relevant Insight

For AI research assistants specifically, the DSL approach solves the exact trust problem that makes researchers hesitant to rely on AI systems. If you can show a researcher the plan — "I'm going to search these 5 databases, using these criteria, and synthesize using this method" — before executing, they can validate the approach. This is qualitatively different from a black-box assistant that returns citations.

💡 The Broader Pattern

The Elicit architecture represents a broader pattern emerging in production AI: moving from end-to-end LLM systems toward hybrid architectures where LLMs handle the parts they're good at (understanding, planning, generating) while deterministic systems handle the parts they're not (precise execution, formal verification, reproducibility).
