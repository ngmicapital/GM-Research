The Prompting Playbook: Eval-Driven Iteration

👤 Margot Vanlar · Applied AI Engineer, Anthropic London 🎓 Code with Claude Conference 2026 · ~34 min 🏷 AI Engineering / Prompt Engineering

Overview

Margot Vanlar, an applied AI engineer at Anthropic's London office, walks through the prompting practices she encounters most frequently with enterprise customers building on Claude. The talk is structured around two practical scenarios: debugging a degraded prompt after a model migration, and building a new agentic workflow from zero. Rather than presenting a list of rules, she demonstrates each practice live with a vibe-coded web app, running actual evals and iterating in real time. The result is one of the most concrete, engineering-grade prompting talks in the conference.

Full Narrative

Scenario 1: Debugging an Existing Prompt

The first scenario is framed around a common real-world situation: a customer support bot for a fictional telco, "Meridian Mobile," that was working well and has started degrading after a model migration. The prompt has accumulated contributions from multiple engineers over time, with no clear owner — a mixture of policy, tone guidelines, patches for old model behaviours, and copied-in website text (including a reference to a "hero image" and even cookie notices).

Margot's first principle: before touching anything, build an eval suite. The eval needs three types of test cases: a control case (something the model should always handle correctly — unambiguous, used to catch regressions), edge cases (specific failure modes that have been seen before and patched), and boundary cases (where the model should refuse or escalate to a human). Her demo suite has five test cases covering a data plan query, a proration bill calculation, a grandfathered plan hotspot question, a billing error that should escalate, and a customer information retrieval test.

Baseline run: The control case passes. Everything else fails.

General hygiene pass: Before targeting specific failures, Margot applies structural improvements. She adds XML tags to separate the prompt into logical sections: <role>, <guidelines>, <policy>, <tone>. She removes the false "you are a human" statement, strips the pasted website content, and clarifies the role description. She also adds an output contract — an XML-tagged response format — plus a stop sequence in the API harness to enforce it. Result: the cleanup alone improves performance. One previously failing test now passes, and scores improve across the board. Her rule of thumb: "If you're reading a prompt and you can't tell guidelines from policy from data, most likely the model isn't able to either."

Failure mode 1 — Hotspot withholding: A customer on a legacy "grandfathered" plan asks how much hotspot data they have. Their account data contains the answer (5 GB). But the model deflects to a URL instead of answering directly. The culprit is a defensive instruction added for an older model: "Never give a customer the wrong plan details — instead point them to the URL." This was a reasonable patch at the time (to prevent hallucinating incorrect plan data), but newer models are much better at instruction-following and are now over-optimising for the instruction, withholding information they actually have. The fix: tell the model explicitly that the customer account data is the authoritative source of truth. After the fix, all hotspot test cases pass. Lesson: models can withhold information they have, not just hallucinate. Use version control on prompts and annotate why defensive patches were introduced.

Failure mode 2 — Proration calculation: A customer asks what their bill will be if they upgrade mid-month. The model does "mental maths" — reasons through it verbally, gets approximate answers, and doesn't return a precise figure the customer can rely on. The original prompt says "critical: always calculate proration correctly" — but telling the model to do a good job doesn't give it the capability to do a good job. The fix: give the model a calculate_proration tool. The tool is defined in the API call with a schema describing inputs and outputs. Once introduced, the model uses the tool reliably and returns correct precise answers. Lesson: instructions don't add capability. For tasks requiring mathematical precision, tools are the right answer.

Failure mode 3 — Billing error escalation: A customer has a billing conflict that should be escalated to a human. The model instead tries to diagnose and explain the discrepancy itself. The original prompt reads: "Avoid escalating or transferring to a care specialist unless absolutely necessary as it costs approximately $8 and counts against our team's fast contract resolution metric." This gives only one side of the trade-off: the cost of escalating. The model optimises for the goal it's given — not escalating. The fix: provide both sides. "It costs $8 to escalate — but if you get this wrong, it costs a refund and customer trust." After the fix, the model escalates billing conflicts reliably. Lesson: as models become more intelligent, state both sides of trade-offs explicitly. Intelligent models will infer and optimise — make sure they have the full picture.

Scenario 2: Building a New Scheduling Agent from Scratch

The second scenario is a retail staff scheduling agent. Given eight employees, a weekly schedule with headcount requirements, and hard constraints that must always be satisfied, the task is to generate a compliant schedule. Because the constraints are deterministic, the eval uses a Python function to count violations rather than an LLM judge.

Margot systematically compares five approaches:

The agentic generate-evaluate-repair loop is the standout winner. Three simple, focused prompts each do one thing: the generator creates a draft schedule; the evaluator checks each rule and provides specific violation evidence (not a programmatic check — an LLM evaluator); the repairer receives the violations and makes targeted fixes. They run sequentially but are each simple and reliable. The result beats both the expensive Opus+thinking approach on token efficiency and beats the better-prompted Sonnet on reliability.

A bonus benefit of the agentic loop: soft constraints can be injected at runtime into the evaluator prompt. "Harry doesn't like working with Sally" or "we need an extra third shift on Wednesday this week" can be added without touching the Python validator. The system is flexible without being fragile.

Key Insights

💡 Insight

Evals are not optional — they are the starting point. Without a rigorous eval suite, you cannot distinguish whether a prompt change is an improvement or a regression. The eval suite is what makes prompt engineering disciplined rather than intuitive. Every prompt-debugging session should begin here, before any changes are made.

💡 Insight

Models withhold as well as hallucinate. The failure mode of a model deflecting a question it could answer is just as harmful as hallucination but receives far less attention. Defensive patches that prevent wrong answers can, as models improve, start preventing correct answers. Both directions of error need to be tested.

🔗 Connection

Connects to the Man Group skills governance lesson. Tashara Fernando (Video 2) warned about patches for old model behaviour persisting and creating dysfunction across the org. Margot makes the same point at the individual prompt level: defensive instructions added for previous models should be version-controlled and annotated so they can be removed when they become counterproductive. The same principle — track why you made a change — applies at both the skill/governance layer and the individual prompt layer.

⚡ Tension

Better prompts vs. agentic decomposition: the prompting ceiling. The comparison between Sonnet 4.6 with a better prompt (2/5 pass, hits token limit) and Sonnet 4.6 in an agentic loop (5/5 pass, lower tokens) is striking. Prompt engineering has diminishing returns on complex multi-step tasks. At some point, the right answer is architectural — decompose the task — not rhetorical. The better prompt approach failed not because the instructions were wrong but because one model in one context has cognitive and output limits.

🔄 Analog

Escalation trade-off design mirrors management science. The insight that models optimise for the goal you give them — and that giving only one side of a trade-off (cost to escalate) produces a biased outcome — is identical to the Goodhart's Law problem in organisations. When a measure becomes a target, it ceases to be a good measure. The prompt engineer's job is to define goals that capture the full trade-off space, not just the metric leadership tracks.

🔄 Analog

Generate-evaluate-repair mirrors test-driven development. The agentic loop — draft, check violations, fix targeted issues — is structurally the same as red-green-refactor in TDD. The insight that separating these phases makes each one simpler and more reliable is a software engineering truth applied to multi-step LLM tasks. The LLM evaluator (not a Python function) adds flexibility: it can check soft requirements that can't be expressed as code.

  • Agentic loop: Three separate prompts — generator, evaluator (LLM), repairer — sequential
  • Soft constraint injection: Added to evaluator prompt at runtime, no Python validator changes needed
  • Version control recommendation: Annotate why defensive prompt patches were added
