The Prompting Playbook: Eval-Driven Prompt Iteration

👤 Margot Vanlar · Applied AI Engineer, Anthropic London 🎓 Code with Claude Conference 2026 · ~34 min 🏷 AI Engineering / Prompt Engineering

First-party practitioner from Anthropic London. Demonstrations are live eval runs on real prompt examples inspired by actual customer prompts. High credibility on engineering practice; business metrics and company names are illustrative.

⚡ The Bottom Line

  • Build evals before touching the prompt. Without a test suite (control cases, edge cases, boundary cases), you cannot tell if a change is an improvement or a regression.
  • Structure beats content — general hygiene alone improves performance. Adding XML tags to separate role/guidelines/policy/tone improved eval scores before any specific failure modes were addressed.
  • Models withhold as well as hallucinate. Overfitted defensive patches from old models can cause newer, smarter models to withhold information they actually have. Both failure directions must be tested.
  • Instructions don't add capability — tools do. "Always calculate correctly" doesn't make a model better at maths. Give it a tool instead.
  • Agentic decomposition outperforms prompt engineering on complex tasks. A generate-evaluate-repair loop with three simple prompts beat both a better-prompted Sonnet 4.6 and an Opus 4.7 with adaptive thinking on token efficiency and reliability.

🔑 Key Claims

1
Prompt structure alone (XML sectioning) improves eval performance before any content changes
Evidence: Live demo: adding XML tags (role/guidelines/policy/tone) to an unstructured prompt improved scores on a 5-case eval suite immediately.
Caveat: Magnitude of improvement depends on how poorly structured the original prompt was. Already-structured prompts gain less.
Consensus: Widely accepted best practice. Margot's live demo provides direct validation.
2
Defensive instructions added for old models can cause newer models to withhold correct information
Evidence: "Never give customer wrong plan details — point to URL" caused the model to deflect a question it had the answer to, in the customer account data.
Caveat: Context-specific. Not all defensive patches become problematic — depends on model version and instruction following capability.
Consensus: Under-discussed. Most focus is on hallucination; this failure mode (withholding) receives less attention.
3
Instructions don't add capability — tools are required for reliable computation
Evidence: "Always calculate proration correctly" failed; introducing a calculate_proration tool with a defined schema fixed it.
Caveat: Applies specifically to precision tasks (maths, lookups). LLMs handle soft reasoning tasks without tools reasonably well.
Consensus: Standard guidance; demonstrated concretely here.
4
Intelligent models need both sides of trade-offs stated explicitly
Evidence: "Avoid escalating — costs $8" caused model to never escalate billing conflicts. Adding "but wrong resolution costs refund + customer trust" fixed it.
Caveat: More important as models become more capable at inference. Older/less capable models may not infer from one-sided goals as aggressively.
Consensus: Emerging best practice for frontier models. Less relevant for older, more literal instruction-followers.
5
Agentic generate-evaluate-repair loop beats single-prompt approaches on reliability AND token efficiency
Evidence: 5/5 pass rate, lower tokens AND lower latency than Sonnet 4.6 with improved prompt (2/5 pass, hit output limit).
Caveat: Requires more system design upfront. Three coordinated prompts with state passing. May not be justified for simpler tasks.
Consensus: Contrarian result — intuition says agentic = more expensive. The data shows otherwise for complex constrained tasks.
6
Evals must cover three case types: control, edge, and boundary
Evidence: Explicitly stated framework from Margot; applied throughout demo.
Caveat: Five test cases is a demo minimum. Real eval suites should be larger and cover full distribution of expected inputs.
Consensus: Standard ML/QA practice applied to prompt engineering.

⚡ Quick Actions

ProtocolSpecWhen / FrequencyKey Detail
Eval-first policyBuild test suite before any prompt changes: control cases, edge cases, boundary casesBefore any prompt migration or debugging sessionMinimum: 1 control, 2 edge, 1 escalation/refusal boundary
Structural hygiene passAdd XML tags to separate role / guidelines / policy / tone / output formatFirst step when inheriting any promptRun eval after — expect improvement before targeting specific failures
Prompt version controlAnnotate why each defensive patch was added; tag with model version it was added forOngoing — every time a defensive change is madeReview annotations when migrating to new model — patches may now cause overfitting
Tool auditFor any task requiring precision (maths, lookups, API calls), replace instructions with toolsWhen debugging calculation or precision failuresDefine tool schema explicitly in API; describe when to use it in prompt
Trade-off balancingFor any goal-directed instruction, state both the cost of the action AND the cost of not taking itWhen reviewing escalation, refusal, or deferral logicEspecially important for frontier models that actively optimise toward goals
Agentic decompositionFor complex multi-step tasks, split into generate → evaluate (LLM) → repairWhen single-prompt approaches hit token limits or reliability ceilingsLLM evaluator (not just Python) allows soft constraints to be injected at runtime
