What this is: The hands-on implementation companion to Ravi's Memory & Dreaming keynote. Kevin walks through creating memory stores via API/CLI, mounting them to sessions, reading the filesystem, running dream jobs, and inspecting memory via the console UI. Key implementation details: choose Opus 4.7 or Sonnet 4.6 for dreaming (quality vs cost); memory files are versioned; ~95% cache hit rate on dream sessions; batch API discount available for lower-cost dreaming.

Implementation Checklist

  1. Create a memory store via API or console — it returns a store ID
  2. Mount the store on a session — specify store ID when creating the CMA session
  3. Agent reads/writes to the mounted filesystem naturally — it uses standard file operations
  4. Inspect via CLI: list memory files, view versions, read current state
  5. Edit memory directly via console UI — correct errors, add context
  6. Create a dream job: specify input memory store + list of session transcripts
  7. Choose model: Opus 4.7 (higher quality) or Sonnet 4.6 (lower cost)
  8. Dream job outputs: new output memory store, enriched and deduplicated
  9. Mount output store to future sessions — agents start with enhanced memory

The Problem Dreaming Solves

⚠ Memory Store Degradation

Without dreaming, memory stores accumulate unbounded over time: duplicate entries, stale information, disorganized structure. Agents dump everything — every task, every observation. The store grows and degrades. Dreaming is the cleanup and enrichment pass: dedup, fact-check, enrich with specific identifiers and dates, reorganize into useful structure.

Console UI Capabilities

  • View memory store as filesystem tree — see directory structure agents created
  • Open and edit individual memory files directly
  • Add new memories manually to any store
  • Browse file version history
  • Launch dream jobs and monitor progress

Actions

  1. Start with a single agent use case where session state loss is costly
  2. Create a memory store, mount it, let the agent run 3-5 sessions
  3. Inspect the store via CLI — see what the agent wrote
  4. Run a dream job with Opus 4.7 against those sessions
  5. Compare the output store to the input — measure the enrichment
  6. Mount the output store to a new session — observe whether the agent performs better
