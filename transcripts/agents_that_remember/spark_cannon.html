What this is: The hands-on implementation workshop for CMA memory stores and dreaming — the practical companion to Ravi's keynote covering the same topics at an architectural level. Kevin (Anthropic engineer on the CMA team) walks through the actual API calls, CLI commands, and console UI for creating memory stores, mounting them to sessions, inspecting memory, and running dream jobs. This is the reference for teams ready to implement, not just understand.

The Problem: Isolated Agents

The baseline problem Kevin frames: today's agents are isolated. Each session starts with no memory of prior sessions. For consumer apps this is often acceptable. For enterprise workflows — customer support, legal research, software development, SRE — agents re-learn context on every session. The cost compounds: re-investigation, re-learning user preferences, re-discovering known failure modes.

The solution has two components:

  1. Memory stores: Persistent filesystem-like stores that agents can read and write across sessions
  2. Dreaming: Async batch jobs that organize, enrich, and deduplicate accumulated memory

Memory Store Implementation

Creating a Store

Memory stores are created via the CMA API or the Anthropic console. Each store gets a unique ID. The store is a persistent filesystem — directories, files, nested structure — that survives between sessions.

Mounting to a Session

When creating a CMA session, you specify which memory store to mount. Not every session needs memory — you choose which sessions get access. The store appears to the agent as a regular filesystem: it reads and writes using standard file operations (bash, read, write).

💡 No Special SDK

The agent doesn't need to know it's using a memory store. It just sees a filesystem path and uses standard file operations. This is by design — agents use familiar primitives rather than a new API.

Agent Behavior

In practice, agents organize memory into a directory structure. They create files for different knowledge categories, update files as they learn new information, and read prior state at the start of each session. Kevin showed an agent that had created subdirectories for customer preferences, known issues, and resolution patterns — a natural organizational structure that emerged from the agent's own use.

Memory Inspection and Editing

Two paths for inspecting memory state:

CLI Inspection

The CMA CLI provides endpoints to list all memory files in a store, read individual files, and view version history. Every write to a memory file creates a new version — the full history is preserved and accessible.

Console UI

The Anthropic console provides a filesystem viewer for memory stores. You can:

  • Browse the directory tree the agent created
  • Open and read individual memory files
  • Edit files directly — correct errors, add context, update stale information
  • Add new memories manually without running a session
  • Browse file version history
💡 Human-in-the-Loop

Direct memory editing via the console UI is a key capability for production deployment. If an agent writes incorrect information to memory, you can fix it without running a new session. This is the human correction mechanism for the memory layer.

Dreaming Implementation

Why Dreaming is Needed

Left to itself, an agent's memory store degrades over time. Agents tend to write frequently — recording every task, observation, and decision. Without a cleanup pass, the store accumulates:

  • Duplicate entries from similar tasks across sessions
  • Stale information that has been superseded
  • Disorganized structure as new categories get added ad-hoc
  • Overly verbose records that slow retrieval

Dreaming is the remediation: a separate batch process whose entire job is to improve the memory store for future use.

Creating a Dream Job

Dream jobs are created via the API or console with the following parameters:

  • Model: Opus 4.7 or Sonnet 4.6. Opus produces higher-quality synthesis; Sonnet is cheaper. Kevin's team typically uses Opus 4.7 for the highest-value stores.
  • Input memory store: The store to dream over (not modified by the dream)
  • Session transcripts: A list of session transcripts to use as enrichment sources

What Dreaming Does

The dreaming harness is a multi-agent system (built by Kevin's team) that:

  1. Reads the input memory store and all specified transcripts
  2. Processes each transcript: fact-checks against stored memories, enriches with additional details (specific identifiers, dates, context), identifies duplicates
  3. Reorganizes memory files for optimal retrieval structure
  4. Produces a new output memory store — the input is never modified
📡 95% Cache Hit Rate

Dream sessions achieve ~95% cache hit rate on the prompt cache. This makes dreaming significantly cheaper than it would appear from the raw model cost — most of the computation is cached across dream runs on similar memory stores.

Cost Optimization

For teams concerned about dreaming cost:

  • Use Sonnet 4.6 instead of Opus 4.7 for lower-quality but cheaper runs
  • Batch API-style scheduling (run at off-peak hours) → 50% cost discount
  • Provide more specific input transcripts (fewer irrelevant sessions) to reduce tokens processed
  • Tighter token budgets via prompt steering

Multi-Agent Memory

Memory stores can be shared across multiple agents in a fleet. Kevin mentioned this in the context of the optimistic concurrency mechanism:

  • Multiple agents can mount the same memory store
  • Writes use optimistic concurrency: version-check before commit, retry on conflict
  • Conflict rates are low for typical agentic workloads (infrequent writes)

This is how the SRE demo (from Ravi's keynote) works: a fleet of agents sharing a single alert-coordination store, writing claims before investigating and resolutions after completing.

Integration Path

Kevin's recommended integration path for teams new to CMA memory:

  1. Identify a single agent use case where session state loss is costly (re-work, re-investigation, user re-explaining context)
  2. Create a memory store and mount it to that agent's sessions
  3. Let the agent run for several sessions — observe what it writes
  4. Inspect via CLI and console — understand the structure the agent created
  5. Run a first dream job — observe the enrichment and reorganization
  6. Mount the output store to new sessions — measure whether agent performance improves
  7. Expand to additional use cases once the pattern is established
⚠ Don't Boil the Ocean

Start with one use case, one memory store, measure the impact. Teams that try to add memory to all agents simultaneously end up with unmanageable stores and no clear measurement of what worked. One case, measure, then expand.
