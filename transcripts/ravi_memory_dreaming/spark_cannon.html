Memory, Dreaming & Persistent Agent State

Ravi · Anthropic · Code with Claude Conference 2026 · May 2026 Agent Infrastructure Memory Dreaming

Core argument: Agents that can't remember are stateless scripts. The Claude Managed Agent (CMA) platform introduces three primitives — persistent memory stores, dreaming (async synthesis), and optimistic concurrency — that together enable agents to accumulate knowledge across sessions, synthesize insights without blocking the agent loop, and coordinate writes safely at scale. Ravi demonstrates a live SRE incident-response agent where a shared memory store prevents duplicate alert handling across an entire agent swarm.

Context & Stakes

The fundamental limitation of current LLM agents is statelessness. Each new session starts cold. For consumer apps this is tolerable — for enterprise agents handling legal research, incident response, or customer support, it's a dealbreaker. Every re-learned fact is wasted compute. Every re-investigated alert is a duplicated incident response.

Ravi leads the API Knowledge team at Anthropic, specifically focused on building the infrastructure layer for agents to interact with persistent knowledge. His team built CMA's memory primitives as a direct response to production pain from Anthropic's largest enterprise customers.

📡 Production Evidence

Rakuten deployed CMA memory stores and saw 97% error reduction. Harvey Law used dreaming to pre-analyze legal session transcripts — their agents went from baseline to 6× benchmark improvement on legal reasoning tasks. Neither number is a lab result.

Memory Stores

Memory stores are file-system-like persistent storage attached to CMA agent sessions. The design choice is deliberately primitive: agents interact via bash and grep, the same tools they'd use for any filesystem. No special SDK. No new abstractions to learn.

This matters architecturally. By mapping memory to filesystem semantics:

  • Agents can use existing bash tooling — find, grep, cat, diff — without modification
  • Memory reads are just file reads; memory writes are just file writes
  • The agent's existing code and prompt patterns work unchanged
  • Debugging memory state is as simple as reading a file
💡 Insight

The filesystem metaphor isn't laziness — it's deliberate. Agents already understand file I/O. By mapping memory to this primitive, Anthropic eliminated an entire learning curve and made memory state trivially inspectable.

Memory stores persist across session boundaries. When an agent session ends, the store survives. When a new session starts — same agent or different agent — it can read the accumulated state. This is the foundation for agents that learn over time.

Dreaming Architecture

Dreaming is the mechanism by which agents process accumulated experience into structured knowledge. It runs as an out-of-band batch process — completely separate from the main agent loop.

The flow:

  1. Agent completes sessions, generating transcripts
  2. Dreaming job picks up transcripts asynchronously
  3. An LLM (typically Opus 4.7) analyzes transcripts for patterns, decisions, and learnable facts
  4. Synthesized summaries are written back to the agent's memory store
  5. Next session starts with enriched memory — agent "woke up smarter"
💡 Key Property

Dreaming is non-destructive. The original transcripts are never modified. If a dreaming run produces a bad summary, you can rerun it without data loss. The memory store always reflects the most recent dreaming run, but rollback is possible.

⚠ Tradeoff

Dreaming introduces a lag between experience and learned knowledge. If an agent makes a critical discovery at 3pm, that knowledge may not be in memory stores until the next dreaming run. For most use cases this is fine. For real-time learning requirements, you need hybrid approaches — real-time writes + batch dreaming for synthesis.

Harvey Law's 6× benchmark improvement came specifically from dreaming. Their agents would analyze depositions and legal documents during the day. Overnight dreaming would synthesize case-relevant patterns, precedents, and strategy notes into memory. Morning sessions started with that accumulated analysis — agents could reason at a higher level from the first token.

Optimistic Concurrency

When multiple agents write to the same memory store simultaneously, you get conflicts. The naive solution — locks — creates bottlenecks that negate the benefits of multi-agent parallelism. CMA uses optimistic concurrency instead.

The protocol:

  1. Agent reads current memory state, notes version number
  2. Agent computes its write
  3. Agent attempts to commit: "write this if version is still X"
  4. If version matches → commit succeeds
  5. If version changed (another agent wrote first) → retry from step 1
📡 Why This Works for Agents

Unlike databases with microsecond write contention, agent memory writes are infrequent (seconds to minutes apart) and semantically meaningful. Conflict rates are low. When conflicts do occur, retrying with updated context often produces a better write — the agent incorporates what the other agent wrote.

💡 Implementation Note

Optimistic concurrency at the agent level is ~10 lines of code. Version-check before commit, catch conflict error, retry. This is worth implementing even in custom memory systems — it's far simpler than locking and handles 95%+ of real-world multi-agent scenarios.

SRE Demo: Shared Alert Coordination

The live demo showed a fleet of SRE agents monitoring different infrastructure components. Classic problem: the same alert fires, multiple agents pick it up, all start investigating the same incident in parallel — duplicated work, potentially conflicting remediation actions.

CMA solution: shared alert-coordination memory store. Protocol:

  1. Alert fires
  2. First agent to pick it up writes "investigating: [alert_id]" to shared memory
  3. Other agents read shared memory before starting — see the claim, skip this alert
  4. Investigating agent writes resolution + learnings back to shared memory
  5. All future agents benefit from the documented resolution pattern

The shared memory turns a fleet of independent stateless agents into a coordinated team that builds institutional knowledge. Each resolved incident enriches the store — the fleet collectively gets better at incident response over time.

💡 Pattern

The "claim before investigate" pattern from the SRE demo is universally applicable to any multi-agent system where work items could be processed by multiple agents. It's a distributed lock implemented via memory — but without the deadlock risks.

Model Selection for Memory Tasks

CMA allows routing different operations to different models. Ravi's recommendation for memory-heavy tasks:

  • Opus 4.7: Memory read/write synthesis, dreaming jobs, complex cross-session reasoning
  • Sonnet: Standard agent tasks, tool use, code execution
  • Haiku: Simple reads, classification, routing decisions

The key insight: Opus 4.7 is currently SOTA specifically for tasks that require understanding large bodies of prior knowledge and synthesizing them coherently. This is exactly what dreaming requires. Don't default to Sonnet for memory synthesis — the quality difference is significant enough to move benchmarks by multiples.

Implementation Patterns

Pattern 1: Session Handoff Memory

At the end of every agent session, write a structured handoff document to memory: what was accomplished, what was attempted but failed, what the next session should prioritize. Next session reads this first. Simple to implement, immediate value.

Pattern 2: Shared Fact Store

For multi-agent systems working on the same domain, maintain a shared fact store. Agents write verified facts with sources. Other agents read before doing research — avoids re-discovering known information. Dreaming periodically synthesizes the fact store for coherence.

Pattern 3: Dreaming Pipeline

Schedule dreaming jobs as a cron — nightly or post-session. Input: accumulated transcripts since last run. Output: structured summaries, extracted patterns, updated strategy notes. Write outputs to a dedicated "synthesized" directory in memory — agents know synthesized content is higher-quality than raw session notes.

Strategic Implications

💡 Strategic Insight

Memory stores + dreaming fundamentally change the economics of agent deployment. A stateless agent has constant per-task cost — no learning, no improvement. A memory-enabled agent amortizes its learning cost across all future tasks. Over time, agents with good memory become significantly cheaper per successful outcome than stateless equivalents.

🔁 Analog

Dreaming is to agents what sleep is to humans — the period where diffuse experiences are compressed into structured long-term memory. The Harvey 6× gain didn't come from a better model; it came from giving the model access to its own organized prior work.

⚠ Open Question

Memory store quality degrades over time if dreaming synthesis is imperfect. Stale or wrong synthesized facts could corrupt future reasoning. Need mechanisms for memory auditing and periodic re-synthesis from raw transcripts. This is an open problem — no clean solution yet.
