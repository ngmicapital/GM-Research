⚡ Verdict

Must-implement for any production agent system. Claude's Managed Agent platform (CMA) solves the three hardest problems in agentic engineering: persistent memory that survives session boundaries, conflict-free multi-agent writes via optimistic concurrency, and async knowledge synthesis via "dreaming." The SRE demo shows real-world impact — shared alert-coordination memory eliminates duplicate incident responses across agent swarms. If you're building agents that need to remember anything across calls, this is the architecture to study.

Key Signals

🔥 Top Signal

Rakuten: 97% fewer errors after switching to CMA memory stores. Harvey Law: 6× improvement on legal benchmarks using dreaming to pre-analyze session transcripts. These aren't benchmark numbers — they're production deployments.

Signal

Opus 4.7 is the current SOTA for file-system style memory tasks. The model selection matters — CMA lets you route memory read/write tasks to the best model for that operation.

⚠ Tension

Dreaming is out-of-band and non-destructive but requires agents to trust that async summaries are accurate. The tradeoff: fresher synthesis vs. potential lag. Ravi's answer: make dreaming idempotent and verifiable.

Core Primitives

  • Memory Stores: Persistent file-system-like storage attached to CMA sessions. Agents read/write with bash and grep natively — no special SDK.
  • Dreaming: Out-of-band batch process that analyzes session transcripts → synthesizes compressed summaries back into memory. Runs asynchronously; doesn't block the agent loop.
  • Optimistic Concurrency: Multi-agent writes use version-check before commit. Conflict → retry, not lock. Scales horizontally without bottlenecks.
  • Sub-Agent Observability: CMA callable agents expose full sub-task traces — you see what sub-agents did, not just the final answer.

Decision Points

When to use dreaming vs. real-time summarization: Use dreaming when synthesis can be async (most cases). Use real-time only when the agent needs the summary before its next action.

When to use CMA vs. custom memory: CMA if you need sub-agent observability + managed infra + out-of-box concurrency. Custom if you have very specific storage or latency requirements.

Multi-agent write conflicts: Optimistic concurrency is correct default. Only move to pessimistic locking if your conflict rate is >20% — most agentic systems won't hit this.

Actions for Your Stack

  1. Audit any agent that currently loses state between sessions — these are prime candidates for CMA memory stores.
  2. For multi-agent systems: implement optimistic concurrency on any shared write path. Version-check + retry is 10 lines of code.
  3. Design dreaming jobs for any agent that accumulates session transcripts — the Harvey 6× gain is low-hanging fruit.
  4. Use Opus 4.7 specifically for memory read/write routing; don't default to Sonnet for these operations.
  5. Instrument sub-agent traces via CMA callable agents — you need to see what sub-agents did to debug production issues.
