Core verdict: The monolithic agent prompt is a dead end. Will's StockPilot case study is the clearest demonstration yet: shrinking a 400-line prompt to 15 lines via skills, replacing 12 custom tools with bash/read/write, and letting sub-agents handle parallelization moved eval scores from 62% to 92%. The architectural principles generalize directly: skills over long prompts, humanlike primitives over custom tools, sub-agents only for parallelization or fresh-eyes review, MCP only when tools need multi-client access.

Decision Rules

Rule 1: Skills over long prompts

Progressive disclosure: Claude pulls skill definitions into context only when needed. A 400-line monolithic prompt loads every instruction on every request. 15 skill stubs load only what's relevant to the current task.

Rule 2: Humanlike primitives first

Before building a custom tool, ask: could a human do this with bash, a text editor, and a web browser? If yes, use those primitives. Custom tools add maintenance overhead and consume context space — use them only for things humans genuinely can't do.

Rule 3: Sub-agents only for parallelization or fresh eyes

Two valid reasons to spawn a sub-agent: (1) work that can be parallelized and (2) tasks that benefit from a clean context (fresh-eyes review, adversarial checking). Don't sub-agent just to decompose complexity — that's what skills are for.

Rule 4: MCP only for multi-client tool sharing

MCP overhead is justified only when multiple clients (agents, apps, services) need to share the same tools. Single-agent tool access should use native code execution or bash — simpler, faster, cheaper.

Rule 5: Code execution over data injection

Instead of fetching data and injecting it into context, write code that queries data on demand. 200K token context of raw data → agent writes a query, gets exactly what it needs. Token reduction is dramatic.

When to Use CMA Callable Agents

CMA callable agents give you sub-agent observability — you can see what sub-tasks the sub-agent took, not just the final answer. Use when: sub-agent failures need to be debugged, sub-agent actions have side effects that need auditing, or the sub-agent's reasoning process matters for compliance.

Actions

  1. Audit your longest agent prompts — anything over 100 lines is a skills refactoring candidate
  2. List all custom tools. For each: could it be replaced with bash/read/write? Probably yes for 60%+
  3. Review sub-agent usage: is each one justified by parallelization or fresh-eyes review? Remove others
  4. Move data access from context injection to code execution — measure the token reduction
  5. Add evals before refactoring, track the 62%→92% pattern on your own systems
