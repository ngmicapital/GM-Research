Agent Decomposition: From Monolith to Modular AI Systems

Will · Anthropic·Code with Claude Conference 2026·May 2026 Agent ArchitectureSkillsSub-Agents

Core argument: The first generation of production agents — monolithic prompts, dozens of custom tools, flat architectures — is hitting a ceiling. Will presents a systematic decomposition methodology that transforms these systems into modular, eval-driven architectures. The StockPilot inventory agent went from 62% to 92% success rate by applying five principles: skills for progressive disclosure, humanlike primitives for tools, sub-agents only for parallelization/fresh-eyes, MCP only for multi-client tool sharing, and code execution over data injection.

StockPilot Case Study

StockPilot is an inventory management agent that monitors stock levels, predicts demand, and triggers purchase orders. Classic first-gen architecture: a 400-line monolithic prompt embedding all business logic, 12 custom tools for every data access and action, no evals, 62% task success rate in production.

Will's team applied the decomposition methodology over several weeks:

  • Week 1: Added evals. Baseline: 62%. Identified top failure categories.
  • Week 2: Extracted business logic into skills. Prompt: 400 lines → 15 lines.
  • Week 3: Replaced custom tools with bash/read/write. 12 tools → 3 primitives.
  • Week 4: Replaced data injection with code execution. Context reduced from 200K tokens.
  • Week 5: Added sub-agents for parallel supplier queries. Eval: 92%.
📡 Key Pattern

Evals first, refactor second. Without a baseline eval score, you can't verify that refactoring improves things. The 62%→92% story only exists because the team measured before and after every change.

Skills: Progressive Disclosure

Skills are packaged information that Claude pulls into context only when needed. Instead of loading every instruction at session start (monolithic prompt), the agent loads a minimal stub for each skill area and fetches full details only when a relevant task arises.

Why this dramatically improves performance:

  • Reduced context noise: The agent sees only instructions relevant to the current task
  • Longer effective context window: Less space used on irrelevant instructions = more space for task data
  • Better instruction following: Focused context → model attends to the right instructions
  • Maintainability: Each skill is a discrete unit; updating one doesn't require touching the others
💡 Structure

Each skill has a short stub (1-3 sentences) that goes in the base prompt, and a full definition that loads when triggered. The agent reads the stub → decides if this skill is relevant → loads full definition if needed. Same progressive disclosure pattern as documentation-on-demand.

⚠ Anti-Pattern

Don't decompose into too many micro-skills. If the agent needs to load 10+ skills for a single task, you've over-decomposed. Target: most tasks load 1-3 skills maximum.

Humanlike Primitives

The most important architectural question for agent tools: could a skilled human do this task using bash, a text editor, and a web browser? If yes, use those primitives directly. Don't build a custom tool.

StockPilot's original 12 custom tools included: get_inventory_levels, get_supplier_prices, get_historical_demand, check_order_status, create_purchase_order, update_inventory_record, get_product_metadata, search_products, get_alerts, update_alert_status, log_action, get_logs.

After refactoring: bash (for file operations and system queries), read (for loading data files), write (for updating records and creating orders). The agent uses these to accomplish everything the 12 tools did — with less code, less context, and higher reliability.

💡 Why Primitives Win

Custom tools have three costs: implementation, maintenance, and context (each tool definition uses tokens). Bash/read/write have near-zero implementation cost, are maintained by the OS, and are described in a few tokens. The model also has extensive training on bash — it uses it fluently without extensive prompting.

Valid reasons to build a custom tool: the action requires an API call with authentication the agent shouldn't handle directly, the tool needs to enforce safety constraints the primitive can't, or the tool wraps a genuinely complex operation that would take many bash commands.

Sub-Agents: Parallelization and Fresh Eyes

Will's framework for when to spawn a sub-agent has exactly two valid reasons:

Reason 1: Parallelization

When a task can be decomposed into independent units that benefit from concurrent execution. StockPilot's supplier price queries: 5 suppliers, each requires an API call, no dependencies between them. A sub-agent per supplier runs in parallel; the orchestrator aggregates results. Wall-clock time drops by 5×.

Reason 2: Fresh Eyes / Adversarial Review

When a task benefits from a clean context that hasn't accumulated the biases of the working session. A sub-agent spun up with only the artifact to review — no history of how it was created — often catches errors the creating agent missed. This is the adversarial reviewer pattern: sub-agent sees the output, not the reasoning that produced it.

⚠ Wrong Reason to Sub-Agent

Don't spawn sub-agents just to decompose complex tasks. Complexity decomposition is what skills are for — they keep everything in one agent's context while still breaking the problem into manageable pieces. Sub-agents add communication overhead; skills don't.

MCP: Only for Multi-Client Tool Sharing

MCP (Model Context Protocol) allows multiple clients to share a common set of tools through a server. It's powerful for the specific case where you want multiple agents, applications, or services to have consistent access to the same capabilities.

It's overkill — and adds unnecessary complexity — when a single agent needs tool access. In that case, native code execution or bash achieves the same result faster, with less overhead, and without the MCP server maintenance burden.

📡 Decision Rule

Ask: "Will more than one client need these tools?" If no, don't use MCP. If yes, MCP is the right choice — consistent interface, centralized updates, single point of maintenance.

Code Execution Over Data Injection

The naive approach to giving an agent data access: fetch the data, inject it into context. This has a hard limit: context windows are finite, and large datasets fill them quickly, leaving less space for reasoning.

The better approach: give the agent code execution capability and teach it to write queries. Instead of injecting 50,000 rows of inventory data, the agent writes a Python query that returns the 10 rows relevant to its current task.

💡 Compounding Benefit

Code execution also improves accuracy. Raw data injected into context is processed by the language model's pattern matching. Data processed by code is processed by deterministic computation. For numerical analysis, aggregations, and filtering, code is both cheaper and more accurate than asking the model to process raw data.

StockPilot went from a 200K token context dominated by raw inventory data to a much smaller context where the agent writes queries and gets targeted results. The reduction in context size compounded with the skills refactoring to make the agent dramatically more focused on each task.

Eval-Driven Development

Will's most consistent message: evals are not optional infrastructure. They're the mechanism by which you know whether you're improving or regressing. The 62%→92% story exists only because evals were in place to measure every change.

Practical eval framework from the talk:

  • Task distribution sampling: 50-100 real examples from production (or production-like) workload
  • Deterministic graders: For tool call correctness, output format, required fields — binary pass/fail, no LLM involved
  • LLM-as-judge: For quality assessment, reasoning correctness, natural language outputs — use a strong model as grader with a detailed rubric
  • Run after every significant change: Prompt edit, tool change, architecture change — run evals, look at the delta
💡 Hill Climbing

The development loop is: make a change → run evals → if score improves, keep; if not, revert or adjust. This is hill climbing on your eval metric. It works because the eval metric is a proxy for production performance — measure carefully.

Strategic Implications

🔁 Software Engineering Analog

The decomposition methodology Will describes maps directly to software engineering's journey from monolithic applications to service-oriented architecture. The same instincts apply: decompose by responsibility, minimize shared state, define clean interfaces. The difference: LLM agents have skills instead of modules, and evals instead of unit tests.

💡 The 62%→92% is Repeatable

The improvement isn't specific to StockPilot — it's a consequence of applying sound architecture principles to a system that was violating them. Any first-gen monolithic agent with these structural problems should see similar gains from systematic refactoring. The methodology is the transferable insight, not the specific numbers.
