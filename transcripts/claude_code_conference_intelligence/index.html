Five Convergent Patterns: What Both Videos Are Really Saying

Videos Analysed 2 of 3 (Video 3 transcript unavailable — new upload)
Domain Agentic AI / Enterprise Implementation

The Convergent Thesis

  • Both videos independently arrive at the same root insight: the constraint is not model intelligence — it is context quality and workflow governance. Fix those, and agents become genuinely powerful. Ignore them, and you get sophisticated chaos.
  • Both videos warn against the same trap: letting individual teams build ungoverned, locally-optimised solutions that can't be shared or composed. Routines solves this at the infrastructure layer; Man Group solves it at the skills layer.
  • Both videos describe the same trust ladder: progressive autonomy earned through demonstrated reliability, not granted upfront.
  • Your organisational context is the moat that no frontier lab can replicate. The work of AI adoption is not learning to use AI — it is exposing your existing institutional knowledge in a form AI can access and act on.

🧱 Pattern 1: The Infrastructure-First Trap

🔄 Cross-Video Pattern Both videos identify the same failure mode: teams default to building their own version of infrastructure-level concerns rather than sharing a common foundation. The cost is duplication, incomparability, and fragility.

Video 1 (Routines): Before Routines, building proactive agents required managing hosting, cron jobs, session state, auth, and observability. Teams spent engineering effort on infra boilerplate instead of domain logic.

Video 2 (Man Group): Before governance, teams each built their own backtest workflows, data cleaning logic, and compute infrastructure. Effort was duplicated; results were incomparable across teams.

💡 Key Insight Before building any agent capability, identify what is "infrastructure" (should be shared, governed, maintained) vs. what is "signal" (the domain-specific logic your team actually owns). Build the infrastructure layer once. Let domain experts focus on signal.

🎯 Pattern 2: Context Is the Ceiling — Consistently

Video 1 (Maya, direct): "Whatever context Claude has, that's the ceiling of how successful Claude will be."

Video 2 (Fernando, direct): "Out of the box, Claude is an amazing general purpose tool. It does a lot, but it doesn't know us. It doesn't know our data. It doesn't know our systems. It doesn't know how we work."

💡 Key Insight Claude's raw intelligence is not the constraint. The constraint is the quality of context it can access at runtime. The competitive advantage is in context, not in the model. Frontier labs cannot give you your organisational context — it's not on the internet. You already have it. The work is exposing it.

Actionable: Treat context assembly as a first-class engineering concern. For every agent workflow, map: What proprietary data does it need? What institutional knowledge must it have? What workflows must it know about? The context map IS the competitive moat.

⚡ Pattern 3: Power User Trap → Governance Must Precede Scale

⚡ Cross-Video Tension Adoption energy is valuable but dangerous without governance structure. Man Group: "everybody was writing skills — adoption was out of this world." Then: expense reports routing to the wrong cost centre. The energy of early adoption will outrun governance if you don't build governance first.

The specific failure mode: The person who can build the skill (power user) is not the person who should own the skill (process owner). These are almost always different people. The power user optimises for themselves. The process owner understands downstream consequences.

Before launching any skills programme:

  1. Map skills to process owners (not to whoever builds them first)
  2. Define: Who reviews? Who approves? Who retires? Who tests?
  3. Establish managed vs. community tiers before the first skill ships
  4. Build a searchable catalogue — visibility is governance infrastructure
  5. Add evals to every managed skill before promotion

🏗️ Implementation Blueprint

Phase 1: Context Mapping

Before any code — identify your iceberg
  • Map the workflows that sit beneath the AI-visible surface of your work
  • For each workflow: what data, terminology, decision rules, and output formats does Claude need?
  • Identify process owners — not "who can build this" but "who is accountable for this in production?"

Phase 2: Governance Architecture

Before first skill ships — build the library
  • Define managed (formal) vs. community (experimental) skill tiers
  • Assign every managed skill to its process owner, not the developer who built it
  • Build a searchable, tagged catalogue visible to everyone — even with 3 skills
  • Write evals for every managed skill before publishing
  • Define the lifecycle: create → draft → review → publish → track → update → retire

Phase 3: Trigger Architecture

Deciding what fires what — schedule vs. event
  • Schedule triggers: What recurring work could Claude do instead? (Docs sync, report generation, backlog review, data pulls)
  • Event triggers: What events in your systems should kick off an agent? (PR merged, issue opened, deploy completed, alert fired)
  • Define context per trigger: what does the agent need when each event fires? What goes in the payload?

Phase 4: Quality Gates

Steerability and verification before you step back
  • Build agent-on-agent review: second Routine triggered by first's PR or output
  • Set your current autonomy stage per workflow (stages 1–5 above)
  • Define the evidence required to advance to the next stage
  • Build output verification into the workflow — render, test, or run Claude's outputs before closing the loop

Phase 5: Scaling

Once the foundation is solid
  • Group skills into domain plugins (Research, Trading, Legal, Engineering, etc.)
  • Track usage — identify what's used, misused, or dormant
  • Enable agent composition: with governed skills, agents can compose them for complex multi-step tasks
  • The Man Group systematic trading pipeline is 4 skills composed: data search → visualisation → backtest → distributed compute
💡 The Single Most Underrated Insight Across Both Videos Man Group: "The frontier labs are not going to solve context for you. It's not on the internet. They don't know your workflows. And you already have that context. You have decades of it. The work is on exposing it, not reinventing it."

The organisations that win the agentic AI transition will not have the best prompts or the fanciest models. They will be the ones that best capture, govern, and expose their existing institutional knowledge. Your workflows are the moat. Skills are the mechanism. Governance is the prerequisite.

Claude Code Routines: Proactive Agents as Teammates, Not Tools

Source Maya, Anthropic Applied AI
Domain AI Engineering / Developer Productivity
Duration ~22 min
Date Code with Claude Conference, 2026

Speakers: Maya — Applied AI team, Anthropic (product & customer deployment) · Sarah (referenced) — Documentation engineer, Anthropic

Full Mode

Executive Summary

  • Coding agents should act, not wait — Routines transforms Claude Code from reactive tool to proactive teammate. The core thesis: "a teammate notices when something breaks and does something about it. A tool waits for you to press enter."
  • Three hard problems with DIY proactive agents are eliminated: hosting (managed infra), triggering (schedule + event), observability (steerable, resumable sessions from web/CLI/desktop).
  • Anthropic's internal docs team is the proof case. Weekly PRs up 200%, one engineer maintaining docs. Sarah automated documentation sync with two Routines.
  • Three decisions define every Routine: trigger (when), context (what Claude knows), steerability (how you keep it honest).
  • Event-based triggers + custom webhooks turn any external system into a Routine trigger. CD pipeline, monitoring alert, Zapier trigger, Slack slash command — all valid without glue code.
  • Agent-on-agent review (generator-critique pattern) is the recommended quality gate — borrowed explicitly from multi-agent system design.
  • Progressive autonomy: watch → steer → review → trust → delegate. Routines are designed for earned, graduated autonomy — not upfront trust.

🧱 The Problem: Three Friction Points in Proactive Agents

"We believe coding agents shouldn't wait for you to press enter to get started."

1. Where do agents run? Running on a local machine means if your laptop closes, the session dies. Managing around this requires hosting, data persistence, and authentication — substantial infrastructure before a single prompt is written. 00:03

2. When do agents trigger? Today's options are cron jobs or custom webhook endpoints you spin up and maintain yourself. 00:04

3. How do you observe and steer them? Headless Claude Code sessions give no real-time visibility. No way to watch, steer, bound, or resume. You either babysit it or fly blind. 00:04

💡 Key Insight The gap between "reactive tool" and "proactive teammate" is not a model capability gap — it's an infrastructure gap. The model can already do the work. Routines abstracts away the scaffolding to trigger, host, and observe it reliably.

⚙️ What Routines Is — Architecture & Capabilities

"It's an automation where you can kick off a remote Claude Code session by only defining the prompt, what repos you want to connect it to, what connectors it has available to work with, and a trigger. Claude Code handles the rest."

Always available: Runs on Claude Code's managed infrastructure. Hosting, session state, connector auth handled by Anthropic. Nothing depends on your laptop. 00:05

Customisable triggers: Time-based (cron schedule) or event-based (GitHub events natively, or custom webhook POST from your own code). 00:05

Interactive and steerable: Every Routine is a regular Claude Code session under the hood. Open on web, CLI, or desktop. Watch live, ask questions mid-session, redirect, resume past sessions. 00:06

🔗 Connection Routines → Claude Code Sessions: "Just a Claude Code session under the hood" means all existing capabilities — tool use, MCP connectors, repo access — are fully available. Routines adds scheduling and lifecycle management on top without replacing the core execution model.

🎯 The Three Decisions Framework

Decision 1: Trigger — When does it run?

Schedule-based: Deterministic periodic runs. "Every Monday, compare source code changes to docs repo and open a PR for any gaps."

Event-based options: Native GitHub events (issue opens, PR merges, label changes, release cuts). Custom webhook: POST from your own code — CD pipeline, monitoring alert, any external system. Event payload passed as context to the session. 00:09–10

💡 Key Insight The custom webhook trigger is underrated. ANY system that can fire a POST request can initiate a Claude Code session with rich context. CI/CD, monitoring alerts, Zapier, Slack slash commands — all become valid Routine triggers without glue code.

Decision 2: Context — What does the agent know?

"Whatever context Claude has, that's the ceiling of how successful Claude will be." 11:46

Practical checklist: one or more repos (read + write), external document stores (Drive, Notion), communication connectors (Slack, email), monitoring tools (Datadog, Grafana), domain-specific MCPs.

Decision 3: Steerability — How do you ensure quality?

Agent-on-agent review: Routine A creates docs PRs. Routine B triggers on PR creation, leaves review comments before humans see it. The generator-critique pattern, natively. 00:12

Live oversight: Open Claude Code on web, watch live, ask questions or redirect mid-run. Demonstrated live — Maya typed "I've already made these changes" and the session stopped. 00:12–17

Output verification: Render the actual page Claude changed. Confirm outputs are what you expect. Build verification into the workflow. 00:13

🔗 Connection Generator-Critique Pattern → Routines: Two Routines with the right triggers = a native two-agent QA pipeline. No custom orchestration code required.

🏗️ Use Cases Demonstrated

Weekly Docs Sync (Anthropic Internal)

Trigger: Every Monday 10am. Repos: Claude Code source + docs repo. Connectors: GitHub (PRs) + Slack (notifications). Result: Claude reads changelogs, finds gaps, opens PRs automatically. 00:07–15

GitHub Issue → Docs Gap Routine

Trigger: issue.opened on docs repo. Prompt: investigate issue, determine if documentation gap, if yes open PR and ping Slack. Event payload (issue content) passed as context. Demoed live — issue created, Routine fires within seconds. 00:15–17

Deploy Verifier

Trigger: CD pipeline POSTs after every deploy. Context: Source code + Datadog/Grafana + Slack/Twilio. Progression: Claude gives go/no-go → human decides rollback → eventually Claude rolls back autonomously. 00:17–20

📋 Routines Protocol Cheat Sheet
  • Create Routine: /schedule in Claude Code terminal → describe in plain English → answer Claude's questions
  • Schedule trigger: "Every Monday at 10am", "Daily at 9am", "Weekly on Fridays"
  • GitHub event trigger: issue.opened, pull_request.merged, push (with label filter)
  • Custom webhook: POST to Routine endpoint from any external system (CI/CD, monitoring, etc.)
  • Context must include: repos needed (source + target), notification connectors (Slack/email), monitoring tools (Datadog MCPs)
  • Quality gate: second Routine triggered by first's PR creation for agent-on-agent review
  • Live steer: open claude.ai web → type directly into running session to redirect or stop
  • Output verification: render/test Claude's output before closing the loop
  • Autonomy progression: define current stage (1-5) and criteria to advance before deploying

Skills Governance Is the Enterprise AI Moat — Man Group's $200B Lesson

Source Tashara Fernando, Head of Data & AI, Man Group
Domain Enterprise AI / Quant Finance / Agentic Systems
Duration ~20 min
Date Code with Claude Conference, 2026

Speaker: Tashara Fernando — Head of Data & AI, Man Group ($200B+ AUM alternative investment manager)

Full Mode

Executive Summary

  • AI-generated trading signals are live in production at Man Group, running real pension capital. Full pipeline — idea generation, data retrieval, backtesting, strategy write-up, productionisation — AI-driven with human review at the end.
  • The tip of the iceberg problem: the signal is easy, the workflows beneath it are everything. Shared backtest infrastructure makes results comparable. Without it, you can't trust your own signals.
  • Man Group got adoption right and governance wrong — and had to rebuild. Power users, not process owners, built early skills. Local optimisations spread org-wide. Skills governance — not adoption — is the real unlock.
  • The fix: a skill library modelled on a real library. Every skill visible, tagged, tested with evals, owned by the workflow owner, tracked, reviewed on a lifecycle, accessible to all.
  • 750 of ~1,700 employees now use Claude Code across every department. 100+ governed skills. Platform now capable of AI-assisted systematic trading at production scale.

💰 What's Actually at Stake

"We manage real people's money — teachers in Canada, metal workers in Japan. If we get this wrong, we could lose real money."

This stakes framing explains why governance is non-negotiable. You cannot apply "move fast and iterate" culture to systematic trading at a $200B AUM regulated firm. The standard for AI outputs is: sensible, reviewed, explainable. 00:00–01

📊 What AI Is Actually Automating in Systematic Trading

A trading signal ranks securities by some factor and goes long the top, short the bottom. Backtest evaluation metrics: annualised return, drawdown (peak-to-trough loss), Sharpe ratio (return vs. volatility). Man Group runs 15+ year historical windows through multiple macro environments. 00:01–04

The full AI-driven pipeline Man Group achieved: AI generated the signal idea → AI retrieved the data → AI ran the backtest → AI wrote the strategy proposal → AI productionised the signal → Humans reviewed for sanity.

"There are trading signals running right now in production at Man Group, a regulated investment firm running real capital, that were researched, backtested and proposed by AI." 04:38
🌐 Consensus Check AI-assisted quantitative research is mainstream at hedge funds. What is notable is the degree of autonomy — the full pipeline end-to-end — and the use of Claude Code as the orchestration layer rather than traditional quant libraries. This represents a meaningful shift from AI-assisted to AI-driven research.

🧊 The Iceberg Problem

"Think of it like an iceberg. The signal is the tip. Underneath it are all of the workflows that make it possible."

Beneath the signal: data cleaning, price stitching, outlier detection, backtest infrastructure, distributed execution, result aggregation. The consistency problem: If Team A runs backtest workflow v1.2 and Team B runs v1.4, results are incomparable — you can't tell if Signal A genuinely outperforms Signal B or just measures differently. 00:06–07

🔗 Connection Iceberg → Skills Governance: The workflows beneath the signal are exactly what skills encode. A well-governed backtest skill means every team runs the same version, producing comparable outputs. The skill is a measurement standardisation mechanism.

❌ The Power User Trap — What Man Group Got Wrong

"It was really the power users that were building the skills. It wasn't the process owners."

Man Group's first wave: workshops, hackathons, show-and-tell sessions, blog posts, Anthropic-assisted training. Adoption was "out of this world." Then the cracks appeared. 00:08–09

The expense report story: A frequent traveller built a skill for expense receipts with Claude. Shared at show-and-tell. Teammates used it. Days later: the Sales expense approver was getting Technology and People Team expenses — because the cost centre code was hardcoded to one user's department. Nobody had reviewed the skill. 00:09–10

"People were just codifying their ways of doing things. They weren't the organisational ways of doing things." 10:46
⚡ Tension At (00:08) Fernando celebrates adoption: "everybody was writing skills, out of this world." At (00:09) that same adoption created dysfunction. The lesson: adoption energy and governance structure must be built simultaneously — governance can't be retrofitted after 100 skills.

✅ The Fix — Skills Governance as the Secret Sauce

The Man Group solution: a common skills marketplace modelled on a library. Every skill has visibility, tagging, evals-based testing, clear ownership (workflow owner, not power user), usage tracking, review process, and a retirement path. 00:11–13

Managed vs. Community tiers: Managed = formally governed, owned by workflow owners, tested, maintained. Community = experimental, visible and cared for, lighter governance.

📜 Analog The library model maps exactly to software package management: npm, PyPI, Homebrew. All solve "anyone can publish, how do we trust it?" with maintainer identity, version history, download counts, deprecation notices. Man Group is building the npm for AI skills — and npm's lesson is that governance matters more than quantity.

📊 The Demo: Credit Card Signal in 4 Skills

1. Alternative data set skill → identifies US consumer credit card transaction dataset
2. Visualisation skill → plots Amazon monthly credit card spend vs. stock price; reveals seasonal correlation (Black Friday, Christmas spikes)
3. Backtesting skill → credit card spend peaks correlate with P&L; $1K in 2021 → ~$2,500; outperforms buy-and-hold
4. Distributed compute skill → scales across broader retail universe; one worker per security, findings collected centrally 00:13–19

💡 Key Insight The distributed compute pattern — one worker per security, centrally aggregated — is a direct consequence of governed shared infrastructure skills. If every team ran their own compute workflow, you couldn't parallelise like this. Governance enables scale.

🎓 What Man Group Would Tell Their Past Selves

  1. Focus on organisational context — it's your IP and moat. "The frontier labs are not going to solve context for you." The work is exposing what you already have. 00:16–17
  2. Treat skills like production code — because they will run in automated pipelines with dependencies. Plan for versioning, testing, deprecation. 00:17
  3. Plan governance before rollout. "Decide this before shipping the first skill, not after the hundredth like us." 00:17
  4. Adoption is a people problem, not a licensing problem. Engagement requires outreach, training, and active cultivation — not just access. 00:17–18
  5. Rethink workflows, don't just augment them. The real value comes from restructuring how work gets done, not layering AI on top of manual processes. 00:18
📋 Man Group Governance Cheat Sheet
  • BEFORE FIRST SKILL: Define ownership (workflow owner, not power user), review process, eval requirements, retirement path
  • Establish managed (formal) vs. community (experimental) skill tiers before launch
  • Build searchable, tagged catalogue visible to all employees — even if it only has 3 skills at launch
  • Every managed skill requires associated evals tested against real workflow scenarios
  • Assign ownership to process owner, not developer who built it — these are almost always different people
  • Track usage: retire unused skills; update skills with high eval error rates
  • Group related skills into domain plugins (e.g., Data, Backtesting, Research, Legal)
  • Golden path: context exposure → governance → skills composability → agent autonomy
  • 4-skill pattern for research: data search → visualise → backtest → distributed compute
