Claude Code Routines — Proactive Agents as Teammates, Not Tools

Maya · Anthropic Applied AI · Code with Claude Conference · ~22 min

Executive Summary

Coding agents should act, not wait — Routines transforms Claude Code from a reactive tool into a proactive teammate. The session introduces Routines, a new Claude Code feature that runs managed, scheduled, or event-triggered agent sessions without requiring any user-maintained infrastructure. The core thesis: "a teammate notices when something breaks and does something about it. A tool waits for you to press enter."

Three hard problems with DIY proactive agents — hosting, triggering, and observability — are all eliminated. Running Claude Code on cron jobs requires managing hosting, session state, authentication, and has no way to watch or steer the agent mid-run. Routines handles all of this on Anthropic's managed infrastructure.

Anthropic's internal docs team is the proof case: weekly PR velocity up 200%, one engineer maintaining docs. Sarah automated documentation sync by creating a routine that runs every Monday, compares source code changes to the docs repo, and opens PRs automatically — with a Slack ping on completion.

Three decisions define every Routine: trigger, context, and steerability. Together they determine how autonomous and reliable the routine becomes.

Event-based triggers unlock reactive architecture without infrastructure. GitHub events (issue opened, PR merged, label applied) or custom POST webhooks can kick off Claude Code sessions.

Agent-on-agent review is the recommended quality gate. One routine creates output; a second routine, triggered by the first's PR creation, leaves review comments before any human sees it.

The end state is progressive autonomy: watch → steer → trust → delegate.

🧱 The Problem: Why Proactive Agents Are Hard to Build Today

"We believe coding agents shouldn't wait for you to press enter to get started."

The talk opens with a diagnosis of three friction points that make building proactive agents painful today:

1. Where do agents run? Running on a local machine means if your laptop closes, the session dies. Building around this requires managing hosting, data persistence, and authentication — a substantial infrastructure investment before you write a single prompt.

2. When do agents trigger? Options today are cron jobs or custom webhook endpoints you spin up yourself. Both require ongoing infra maintenance — hence the joke about the one person in the audience who enjoyed maintaining their cron job.

3. How do you observe and steer them? Headless Claude Code sessions give no real-time visibility. There's no way to watch, steer, bound, or resume a running session. You either babysit it or fly blind.

💡 Key Insight The gap between "reactive tool" and "proactive teammate" isn't a model capability gap — it's an infrastructure gap. The model can already do the work; what's missing is the scaffolding to trigger, host, and observe it reliably. Routines is Anthropic's answer to abstracting that scaffolding away entirely.

⚙️ What Routines Is — Architecture & Capabilities

"It's an automation where you can kick off a remote Claude Code session by only defining the prompt, what repos you want to connect it to, what connectors it has available to work with, and a trigger. Claude Code handles the rest."

Routines is a managed execution layer for Claude Code sessions built on three design principles:

Always available: Routines run on Claude Code's managed infrastructure. Hosting, session state, and connector auth are handled by Anthropic. Nothing depends on your laptop.

Customisable triggers — two types:

  • Time-based: Run on a cron schedule (e.g., every Monday at 10am)
  • Event-based: Trigger on GitHub events (issue opened, PR merged, release cut, label applied) or custom webhook POSTs from your own code/CD pipeline

Interactive and steerable: Every Routine is a regular Claude Code session under the hood. You can open it on web, CLI, or desktop, watch it work in real time, ask questions mid-session, push it in a different direction, and resume past sessions.

🔗 Connection Routines → Claude Code Sessions: The "just a Claude Code session under the hood" framing is important. It means all existing Claude Code capabilities — tool use, MCP connectors, repo access — are fully available. Routines adds scheduling and lifecycle management on top, it doesn't replace the core execution model.

The setup flow via /schedule:

  1. Type /schedule in Claude Code terminal
  2. Describe the task in plain English
  3. Claude asks clarifying questions (timing, notification preferences)
  4. Claude generates structured instructions and creates the routine
  5. View, manage, and observe from claude.ai web interface

🎯 The Three Decisions: Trigger → Context → Steerability

Decision 1: Trigger

Schedule-based: Used for periodic reviews — "every Monday, compare source code changes to docs repo and open a PR for any gaps." Deterministic, easy to reason about.

Event-based options:

  • Native GitHub events: issue opens, PR merges, label changes, release cuts
  • Custom webhook: POST from your own code (e.g., CD pipeline fires after every deploy)
  • The event payload is passed as context to the Claude Code session
💡 Key Insight The event-based webhook trigger is underrated. It means ANY system that can fire a POST request can now initiate a Claude Code session with rich context. CI/CD pipeline, monitoring alert, Zapier trigger, Slack slash command — all become valid Routine triggers without writing any glue code.

Decision 2: Context

What does your agent need to know to succeed? The ceiling of Routine success is the ceiling of its context.

"Whatever context Claude has, that's the ceiling of how successful Claude will be."

Practical context checklist:

  • One or more codebase repos (read + write access for PRs)
  • External document stores (Google Drive, Notion) for reference material
  • Communication connectors (Slack, email) for notifications
  • Monitoring tools (Datadog, Grafana) for health-check routines
  • Domain-specific MCPs for specialised capabilities

Decision 3: Steerability

How do you ensure quality without babysitting?

Agent-on-agent review (recommended): One Routine creates docs PRs. A second Routine triggers on PR creation and leaves review comments before humans see it. This is the generator-critique pattern from multi-agent system design.

Live oversight: Open Claude Code on web, watch the session live, ask questions or redirect mid-run. You can tell Claude to stop in real time.

Output verification: For the docs example, render the actual documentation page Claude changed and confirm it looks right. Build verification into the workflow, not just the prompt.

🔗 Connection Generator-Critique Pattern → Routines: The agent-on-agent review maps directly to the classical AI safety pattern. Routine A generates; Routine B critiques before human review. This is a native two-agent QA pipeline that requires no custom orchestration code — just two routines with the right triggers.

Context: Claude Code PR velocity up 200% YoY. One engineer maintaining docs for Claude Code and Agent SDK.

  • Repos: Claude Code source + docs repo
  • Connectors: GitHub (PR creation), Slack (notifications)

  • Trigger: issue.opened on the Claude Code docs repo
  • Prompt: Investigate the issue, determine if it's a documentation gap, if yes open a PR and ping Slack
  • Demo moment: Maya creates a test issue, Routine fires within seconds

Use Case 2: Deploy Verifier

  • Trigger: CD pipeline POSTs to Routine webhook after every deploy
  • Context: Source code for deployed service + Datadog/Grafana connector + Slack/email/Twilio for alerts
  • Steerability progression:
    1. Start: Claude investigates and gives go/no-go recommendation
    2. Mid-stage: Human reads analysis in web UI, decides whether to roll back
    3. Mature stage: Claude rolls back automatically, human notified post-facto
"Maybe eventually as I watch Claude work more and more and trust its decisions, I can let Claude roll back the change itself."

Use Case 3: On-Call Investigator

  • Trigger: Monitoring alert or schedule
  • Context: GitHub issues, Slack channel, internal runbooks
  • Behaviour: Reads and triages backlog, prioritises, opens PRs for critical issues

Use Case 4: PM Backlog Reviewer

  • Trigger: Weekly time-based
  • Context: GitHub issues + Slack threads
  • Behaviour: Reads all open issues, surfaces prioritised list, optionally opens PRs for the most important ones
💡 Key Insight Each use case follows the same three-question structure: What triggers it? What context does it need? How do I keep it honest? This is a portable design pattern — the "Routine Design Canvas" — that can be applied to any recurring or event-driven workflow.

📈 The Autonomy Progression Model

Maya describes a spectrum of human involvement that maps cleanly to levels of trust:

1. WatchObserves Claude working in real timeExecutes, reports

📜 Analog This autonomy progression mirrors how you onboard a human junior engineer. You pair-program first (watch), then review their PRs (steer/review), then approve merges without reading every line (trust). The Routine is a new-hire that earns autonomy through demonstrated reliability.

Skills Governance Is the Enterprise AI Moat — Man Group's $200B Lesson

Tashara Fernando · Head of Data & AI, Man Group · Code with Claude Conference · ~20 min

Executive Summary

Man Group has AI-researched trading signals running live in a regulated investment firm managing real people's pension money. The full pipeline — idea generation, data retrieval, backtesting, strategy write-up, productionisation — was executed by AI with human review at the end. This is not a prototype.

The tip of the iceberg problem: the signal is easy, the workflows beneath it are everything. Coming up with a trading signal idea is "the quick bit." The hard part is the 10+ underlying workflows that make it executable and comparable.

Shared workflows are a competitive moat — and Claude can't give them to you. Frontier labs don't know your data, your systems, or your processes. Organisational context — decades of institutional knowledge — is "one of the few safe spaces left in AI."

Man Group got adoption right and governance wrong — and had to rebuild. Power users, not process owners, built the early skills. The result was local optimisations masquerading as shared solutions.

The fix: a skill library modelled on a real library. Every skill is visible, tagged, tested with evals, owned by the workflow owner, tracked for usage, and reviewed on a lifecycle.

750 of ~1,700 Man Group employees now use Claude Code across every department. 100+ governed skills, 100+ community skills.

The golden path: organisational context → governed skills → agentic capability. The sequence matters. You cannot build reliable agents on top of ungoverned, locally-optimised skills.

💰 What's Actually at Stake — Stakes Framing

"We manage real people's money — teachers in Canada, metal workers in Japan. If we get this wrong, we could lose real money."

Fernando opens with deliberate stakes-setting: this is regulated capital, real pensions, real consequences. This framing explains why governance is non-negotiable. You cannot deploy "move fast and iterate" culture to systematic trading at a $200B AUM firm. The standard for AI outputs is: sensible, reviewed, explainable.

💡 Key Insight The stakes framing is itself a governance argument. When the cost of a bad AI output is someone's pension drawdown, the quality bar for skills is fundamentally different from when the cost is a bad Slack summary. Know your stakes; design your governance accordingly.

📊 Systematic Trading — What AI Is Actually Automating

"Think of a signal like a fantasy football team."

Fernando's analogy: a trading signal ranks securities by some factor and goes long the top ones, short the bottom ones. The quality depends on the factor (what you're ranking by), rigorous backtesting (15+ years of history), and comparability (if different teams run different backtest versions, results are meaningless).

The full AI-driven pipeline Man Group achieved:

  1. AI generated the signal idea
  2. AI retrieved the data
  3. AI ran the backtest
  4. AI wrote the strategy proposal
  5. AI productionised the signal
  6. Humans reviewed the output for sanity
"There are trading signals running right now in production at Man Group... that were researched, backtested and proposed by AI."

🧊 The Iceberg Problem — Workflows Are the Hard Part

"Think of it like an iceberg. The signal is the tip. Underneath it are all of the workflows that make it possible."

The iceberg model is the conceptual core of the talk. The visible signal is easy to generate. The invisible infrastructure beneath it is what makes it executable and comparable:

  • Data cleaning workflows
  • Price stitching routines
  • Outlier detection algorithms
  • Backtest infrastructure (what compute does it run on?)
  • Distributed execution patterns
  • Result collection and aggregation

The consistency problem: If Team A runs backtest workflow v1.2 and Team B runs workflow v1.4, their results are incomparable. You can't tell if Signal A genuinely outperforms Signal B, or if Team A's workflow just measures differently.

🔗 Connection Iceberg → Skills Governance: The workflows beneath the signal are exactly what skills encode. A well-governed backtest skill means every team runs the same version, with the same parameters, producing comparable outputs. The skill is not just a productivity tool — it's a measurement standardisation mechanism.

❌ What Man Group Got Wrong — The Power User Trap

"It was really the power users that were building the skills. It wasn't the process owners."

Man Group's first wave looked like success: workshops, hackathons, show-and-tell sessions. Adoption was "out of this world." And then the cracks appeared.

The expense report story (the canonical failure case):

  • A frequent traveller built a skill to process expense receipts with Claude
  • He shared it at show-and-tell; teammates loved it; they started using it
  • Days later: the expense approver for Sales complained that Technology and People Team expenses were coming to her cost centre
  • Root cause: the cost centre code was hardcoded to the original developer's department
  • Nobody had reviewed the skill. It worked for him. He assumed it would work for everyone.

Why this matters beyond the anecdote:

  • Power users optimise for themselves, not the organisation
  • They're often not the process owners — they don't know the downstream consequences
  • Unreviewed skills spread virally without quality gates
  • In backtesting: different teams use different data cleaning logic → results become incomparable
  • Agents can't leverage these skills because there's no commonality to build on
"People were just codifying their ways of doing things. They weren't the organisational ways of doing things."
⚡ Tension Fernando celebrates the adoption wave: "everybody was writing skills, adoption was out of this world." Then she describes how that same adoption created dysfunction. The tension: you need adoption energy AND governance structure simultaneously, but most organisations discover governance need only after adoption has already gone wrong.

✅ The Fix — Skills Governance as the Secret Sauce

"Skills governance started to be the secret source that unlocked these enterprise use cases."

The Man Group solution: a common skills marketplace modelled on a library. Every skill has:

  • Visibility: All skills searchable and browsable by everyone
  • Tagging: Skills categorised by department and function
  • Testing with evals: Every skill has associated evaluations for quality assurance
  • Clear ownership: The skill is owned by the workflow owner (not the power user who built it)
  • Usage tracking: How often is each skill being used? By whom?
  • Review process: Skills are reviewed on a lifecycle — not shipped and forgotten
  • Retirement path: Skills have an end-of-life process

Managed vs. Community skills:

  • Managed skills: Formally governed, owned by workflow owners, tested, maintained
  • Community skills: More experimental, still visible and cared for, but lighter-weight governance

Plugins as skill bundles: Skills can be grouped into plugins (e.g., a "Data" plugin that gives access to Man Group's alternative data sets). This lets users install a whole capability set in one action.

📜 Analog The library model maps exactly to software package management. npm, PyPI, and Homebrew all solve the "anyone can publish, how do we trust it?" problem with governance: maintainer identity, version history, download counts, issue tracking, deprecation notices. Man Group is building the npm for AI skills — and npm's lesson is that governance matters more than quantity.

📊 The Demo: Credit Card Signal Research in 4 Skills

Fernando walks through a live demo of building a systematic trading signal using the governed skills platform:

#SkillWhat It DoesOutput
1 Alternative data set skill Search Man Group's proprietary data catalogue Identifies US consumer credit card transaction dataset
2 Visualisation skill Plot Amazon monthly credit card spend vs. stock price returns Reveals seasonal correlation pattern (Black Friday, Christmas spikes)
3 Backtesting skill Compare credit card spend peaks to P&L of the stock Signal outperforms buy-and-hold; $1K → ~$2.5K since 2021
4 Distributed compute skill Scale backtest across broader retail universe with individual workers per company Result: signal holds across broader universe, not just Amazon

The key point: four skills, fully governed, each owned by the relevant team. The quant researcher doesn't need to know how distributed compute works — they just install the skill.

💡 Key Insight The distributed compute pattern — one worker per security, centrally aggregated — is a direct consequence of having governed, shared infrastructure skills. If every team ran their own version of the compute workflow, you couldn't parallelise like this. The backtest infrastructure skill is what enables scale.

🎓 What Man Group Would Tell Their Past Selves

Fernando's explicit takeaways — the most distilled, practitioner-tested advice in the talk:

1. Focus on organisational context — it's your IP and your moat.

"The frontier labs are not going to solve context for you. It's not on the internet. They don't know your workflows. And you already have that context. You have decades of it. The work is on exposing it, not reinventing it."

2. Treat skills like production code — because that's what they become. They will run in automated pipelines. They will have dependencies. They will need versioning, testing, and deprecation. Plan for this from day one.

3. Plan governance before you plan rollout. Who owns each skill? Who reviews it? How does it get retired? How is it tested? Decide this before shipping the first skill, not after the hundredth.

4. Adoption is a people problem, not a licensing problem. Once the platform exists, engagement requires outreach, training, and active cultivation — not just access.

5. Rethink workflows, don't just augment them. The real value comes from restructuring how work gets done, not just adding AI on top of existing manual processes.

📋 Protocol Cheat Sheet

The Man Group Governance Model Checklist

(Apply before your 2nd skill, not your 100th)

  • Identify the workflow owner (not the power user — the actual owner)
  • Assign formal ownership of the skill to that person
  • Write evals for every managed skill before publishing
  • Track usage — retire skills that aren't used; update skills that are misused
  • Separate managed skills (formal) from community skills (experimental)
  • Group related skills into plugins for easier installation
  • Build a searchable, tagged catalogue visible to everyone
  • Establish a skill lifecycle: create → review → publish → track → update → retire

The Golden Path to Agentic Capability

  1. Capture organisational context in skills
  2. Govern those skills (ownership, testing, lifecycle)
  3. Connect skills to data and compute capabilities
  4. Enable agents to compose skills for complex tasks
  5. Iterate toward agent swarms for autonomous exploration

Credit Card Signal Demo — The 4-Skill Pattern

  1. Alternative data search skill (find the dataset)
  2. Visualisation skill (see the correlation)
  3. Backtesting skill (validate the signal)
  4. Distributed compute skill (scale across universe)
