How We Claude Code: HTML Specs, Verification & Agent-Native Workflows

Ara · Anthropic Applied AI·Code with Claude Conference 2026·May 2026 Claude CodeHTML SpecsVerificationWorkshop

Core argument: The way Anthropic's own Claude Code team builds software is a three-phase loop: interactive spec extraction via AskUserQuestion, visual exploration via HTML design directions, and agent-native verification via Storybook fixtures + Playwright MCP. This is built on "The Unreasonable Effectiveness of HTML Files" — the insight that rich, interactive artifacts communicate intent far better than markdown, enabling faster iteration with fewer misalignments.

Context

Ara is an architect on Anthropic's Applied AI team. This workshop is based on a talk by "Tar" (a team member) published as a blog post called "The Unreasonable Effectiveness of HTML Files" — arguing that the field should move from markdown-centric workflows to HTML-first development with Claude. Ara presents the three-phase workflow that Tar's team uses in production, with a live coding demo on a bill-splitting app and a to-do app verification framework.

📡 Source Reference

The methodology is from the Claude Code team's internal practice, published approximately 1.5 weeks before this conference as a blog post. The workshop repo (CWC Workshops / "how we claude code") contains all three phases with detailed documentation.

Settings: Non-Negotiables

Before any other workflow: three settings that Ara treats as non-negotiable.

  • Auto mode: Always use auto mode in Claude Code. It dramatically simplifies the interaction model. Ara specifically called this out to the audience and confirmed everyone should be using it.
  • Effort parameter: Set to X-HIGH. The team's standard recommendation. MAX effort also works — it's even more thorough.
  • Model: Opus 4.7 for any work involving visual feedback or frontend development. The improved vision model is what makes the screenshot feedback loop effective.

Fast mode is also recommended during HTML spec generation — it costs more per token but the faster iteration speed is worth it when exploring design directions.

Phase 1: Interactive Spec Extraction

The core insight: the longer an agent run you're planning, the more important it is that the spec is comprehensive — and the less likely you are to upfront-specify everything correctly without help.

Solution: prompt Claude to use the AskUserQuestion tool to interview you on requirements before generating anything. Claude asks turn-by-turn questions; you answer incrementally. By the end, Claude has extracted a far more complete picture of what you want than you could have written in a single upfront prompt.

💡 Prompt Pattern

In your initial prompt, explicitly reference the AskUserQuestion tool and instruct Claude to use it to extract requirements. The more specific this instruction, the better the interview will be. The repo contains example prompts for this pattern.

The workflow then continues: Claude generates a spec from the interview. That spec is the input to Phase 2.

Phase 2: HTML Design Exploration

Rather than committing to implementation from a text spec, generate 4 different HTML design directions first. This is the "Unreasonable Effectiveness of HTML Files" insight in practice.

Why HTML over markdown specs:

  • Information density: A visual prototype communicates layout, interaction, and aesthetic in a single artifact. A markdown spec requires the reader to mentally simulate all of this.
  • Readability: Markdown specs over ~200 lines don't get read — by you or your colleagues. HTML files get opened and clicked through.
  • Feedback precision: Giving Claude feedback on "the button is slightly misaligned" or "this aesthetic isn't right" is far easier when you can screenshot the rendered HTML and show it, rather than trying to articulate it from a markdown description.
  • Opus 4.7 vision: The improved vision model makes screenshot → feedback → iterate loops highly effective for frontend alignment.
💡 The 4-Direction Prompt

Ask Claude to "explore 4 different design directions, generate each as HTML, and annotate the design philosophy of each." You get visual options across aesthetic dimensions (brutalist, refined, minimal, expressive) before committing to any direction. Much faster than discovering the direction was wrong mid-implementation.

⚠ Common Objection: Token Cost

HTML specs use more tokens than markdown on initial generation. The rebuttal: you iterate less with HTML specs because visual miscommunication is caught early. Over the full build cycle, HTML specs reduce total token spend. The right unit is cost per shipped feature, not cost per spec generation.

Phase 3: Agent-Native Verification

This is the most sophisticated part of the workflow, and what makes it "agent-native" rather than just "Claude-assisted."

The Core Concept: DOM as Data Contract

Rather than writing traditional tests that Claude then has to understand and run, the team embeds data contracts directly into the DOM using data attributes. Each component exposes its expected state through these attributes — making the component's behavior machine-readable without requiring Claude to understand the test framework.

With this structure, Claude uses Playwright MCP to navigate the app, read the data attributes, and verify that actual state matches expected state. It doesn't need to understand React, the component library, or the test runner — it just reads DOM attributes.

The Verification Artifact

Verification runs are recorded. The recording becomes a shareable artifact — a video or log that colleagues can review to see exactly what the agent verified and how. This is how the Claude Code team provides verification evidence without requiring human re-running of tests.

💡 Storybook Integration

Storybook fixtures provide the isolated component environment where Claude can test each component state independently. Combined with data attributes, each Storybook story is a precise, machine-readable specification of a component's expected behavior in a given state.

📡 Playwright MCP Role

Playwright MCP gives Claude browser control: navigate to the Storybook story, interact with the component, read the data attributes, compare to expected values, report pass/fail. The agent generates and runs the verification — minimal human touchpoints once the fixtures are in place.

The Full Loop

  1. AskUserQuestion interview → comprehensive spec
  2. HTML design directions → visual exploration, screenshot feedback
  3. Implementation with data attributes embedded in DOM
  4. Storybook fixtures for each component state
  5. Playwright MCP verification run, recorded as artifact
  6. Iterate on failures, re-run verification

The loop gets tighter over time because: (a) the spec is comprehensive from Phase 1, (b) the visual alignment is confirmed in Phase 2, and (c) failures in Phase 5 are precise and machine-verifiable.

Implications

🔁 Analog: Infrastructure as Code

Making your app agent-native via data attributes is analogous to Infrastructure as Code — you're making system state machine-readable so it can be managed programmatically. The same instinct (make implicit state explicit) applies to both.

💡 The Modularity Point

Ara briefly notes that sensible modularization is key to making Phase 3 scale — each component in its own Storybook story, data contracts per component, no cross-component dependencies in the fixture state. This becomes clear from the repo. The principle: design your app for the agent to verify, not just for humans to use.

Three Phases

  1. Interactive spec extraction: Prompt Claude to use the AskUserQuestion tool to interview you on requirements. Claude asks turn-by-turn; you don't need to upfront-specify everything. The longer the agent run you're planning, the more important this is.
  2. HTML design exploration: Ask Claude to generate 4 different visual design directions as HTML files. Click through them. Give feedback on aesthetics directly. Far more information-dense than markdown specs — and colleagues actually read them.
  3. Agent-native verification: Build Storybook fixtures + data-attribute DOM contracts into the app. Claude uses Playwright MCP to run verification, records results. Verification is generated and run by the agent — minimal human touchpoints.

Settings That Matter

  • Auto mode: Always. Non-negotiable per Ara.
  • Effort: X-HIGH recommended; MAX also works. Never default.
  • Fast mode: Use during HTML spec generation — costs more, worth it for quick iteration
  • Model: Opus 4.7 for vision-heavy frontend work. Better vision than prior models.

Key Insight: HTML Specs Are Not Token-Inefficient

💡 Counterintuitive

HTML specs use more tokens than markdown on a single generation. But in the long run, you iterate less — the visual spec communicates so much more that misalignments are caught early. Net token cost over the full build cycle is lower with HTML specs.

Screenshot Feedback Loop

Take screenshots of the rendered HTML → feed back into Claude. Especially effective with Opus 4.7's improved vision for catching frontend misalignments you can't easily articulate in words. This is the team's standard practice.

Agent-Native Verification Pattern

💡 The Key Move

Don't write tests for Claude to verify. Write data contracts in the DOM — data attributes and fixtures that make the component's expected state machine-readable. Then Claude can use Playwright MCP to verify without needing to understand the test framework. The verification steps get recorded as shareable artifacts.

Actions

  1. Set auto mode and effort=X-HIGH as your permanent Claude Code defaults
  2. On your next feature: use AskUserQuestion to interview yourself on requirements before writing code
  3. Generate 4 HTML design directions before committing to implementation
  4. Add data attributes to your DOM that expose state contracts — make your app agent-readable
  5. Use Playwright MCP for Claude-driven verification and record the sessions
