Core argument: The default mental model for model selection — pick the cheapest model that works — is wrong. The right metric is cost per successful outcome, which accounts for retry rates, accuracy, and the compound cost of failures. Applied rigorously, this framework often selects Opus 4.7 over Sonnet for complex tasks. Combined with prompt caching (10× cost reduction at 80-90% hit rate) and context engineering (66-77% token reduction), the economics of LLM deployment look radically different than naive per-token pricing suggests.

The Core Reframe: Cost Per Successful Outcome

Most teams optimize for cost-per-token or cost-per-request. Lucas argues this is the wrong unit entirely. The correct optimization target is cost per successful outcome.

Why the distinction matters: a cheaper model that succeeds 60% of the time costs significantly more per successful outcome than an expensive model that succeeds 95% of the time — especially when failures have downstream costs (retries, human review, wrong actions taken).

📡 The Opus 4.7 Paradox

Opus 4.7 is more expensive per token than Sonnet. But on complex reasoning tasks, Opus 4.7 often completes tasks in fewer attempts, uses fewer total tokens (because it doesn't go down wrong paths), and produces outputs requiring less correction. Net result: Opus 4.7 is frequently cheaper per successful outcome for complex tasks, and often faster in wall-clock time because it doesn't require retry loops.

The practical implication: before defaulting to Sonnet, run both models on your actual task distribution with your actual success criteria. Measure outcomes, not just tokens. The results will often surprise you.

Prompt Caching: The 10× Lever

Prompt caching allows the API to reuse computation on repeated context. Cached tokens cost roughly 1/10th of normal tokens. At 80-90% cache hit rate — Lucas's target for well-designed systems — this translates to an order-of-magnitude reduction in effective cost.

The Append-Only Pattern

Cache hit rate is determined by how often the cache prefix matches. The single most important implementation choice: never modify earlier turns in a conversation. Only append. When you modify earlier turns, you invalidate the cache for everything after that point.

Practical rules:

  • System prompt: completely stable, goes first, always cached
  • Reference documents injected at session start: stable, cached after first request
  • User messages: append only, never edit
  • Tool results: append after tool call, never modify prior calls
  • Dynamic content: always goes last — it changes every request, can't be cached
💡 Engineering Target

80-90% cache hit rate is achievable for most agentic applications with disciplined append-only patterns. Below 60% means something is changing in the cached prefix — audit your message construction logic.

⚠ Common Failure Mode

Injecting timestamps, request IDs, or dynamic metadata into system prompts. This invalidates the cache on every request. Remove all dynamic content from system prompts; put it in the user turn.

Context Engineering: Token Reduction Without Accuracy Loss

Context engineering is the practice of optimizing what goes into the context window — both to reduce token cost and, often, to improve accuracy. Lucas presented two concrete examples with measured results.

Tool Response Format: JSON → Markdown

Most tool responses default to JSON. JSON is verbose: field names repeated, brackets and quotes everywhere. Switching tool responses to markdown (or plain text for simple values) achieved a 66.4% token reduction in Lucas's measurements.

Critically, model performance did not degrade — if anything, it improved, because markdown is closer to the natural language the model was trained on.

💡 Implementation

For each tool, define a markdown formatter alongside the JSON schema. The model receives markdown; your logging/storage layer can still use JSON. This is a single-pass transformation with no architectural changes required.

Web Search Deduplication

Multiple web searches on related queries often return overlapping results — the same article or data point surfaced from different queries. Injecting all results raw means the model sees duplicate information, which:

  • Wastes tokens on content already in context
  • Creates contradictory signals that confuse model reasoning
  • Artificially inflates confidence in repeated claims (seeing the same fact 3x looks like 3 sources)

Adding a deduplication step before context injection (simple URL-based or embedding-based similarity) achieved: 77% input token reduction, 65% cost reduction, 9% accuracy improvement.

💡 The Accuracy Gain

The 9% accuracy improvement is counterintuitive — you'd expect removing content to hurt accuracy. But deduplication removes noise and reduces contradictory signals, letting the model reason from a cleaner evidence set.

Thinking vs Effort Parameters

Claude's extended thinking capability is controlled via two parameters that operate at different levels of abstraction.

Thinking parameter: Direct control over the reasoning budget in tokens. Higher values allow more computation before producing a response. Best for teams who understand their task's compute requirements and want fine-grained control.

Effort parameter: Higher-level abstraction that maps intuitive effort levels to appropriate thinking budgets. "High effort" automatically allocates more thinking tokens than "low effort." Best for most applications — it's human-interpretable and doesn't require understanding token-level compute requirements.

🔁 Analog

Thinking parameter is like specifying CPU time limits directly. Effort parameter is like telling someone "think carefully about this" — the system translates the intent to the right resource allocation. Use effort unless you have a specific reason to control compute directly.

Model Selection Decision Framework

Lucas's practical framework for model selection:

  1. Define success: What does a successful outcome look like for your task? Be specific — correct answer only, or also correct format, no hallucination, within latency target?
  2. Sample your task distribution: Take 50-100 real examples from production (or expected production) workload.
  3. Measure success rate per model: Run each candidate model on your sample. Record success rate, average tokens used, wall-clock time.
  4. Calculate cost per successful outcome: (token cost) / (success rate). Include retry costs if applicable.
  5. Select on economics, not intuition: The model with the best cost-per-successful-outcome wins, regardless of tier.
⚠ Important Caveat

Task distribution changes over time. A model selection made on today's distribution may be wrong in 6 months as usage evolves. Build model selection re-evaluation into your regular engineering cadence, not just initial launch.

Strategic Implications

💡 Combined Effect

Stacking these optimizations compounds: correct model selection (Opus on complex tasks) + prompt caching (10× on cached tokens) + context engineering (66-77% token reduction) can produce effective cost reductions of 95%+ vs naive implementation. The gap between teams that do this engineering work and those that don't is enormous.

📡 Connection to Agent Architecture

In multi-step agentic systems, context engineering compounds at each step. If each tool call reduces token overhead by 66%, a 10-step agent reduces total context by ~90% vs a naive implementation. The economics of agentic AI look very different once this work is done.
