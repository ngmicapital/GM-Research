Core reframe: Evals aren't a testing phase — they're a continuous dev flywheel. Build rubric-driven replayable evals early, use LLM-as-judge for taste, and hill-climb on score deltas. The 6-hour setup cost pays back immediately: you go from "it feels worse" to "it's 12% worse on clarity — here's why." The slide-generation agent case study shows how real user dissatisfaction signals, encoded as evals, become the engine of rapid iteration.

What Evals Give You

  • Quality signals: What's good, what's bad, and how much — not just pass/fail
  • Actionability: "Vibes are worse" → "Clarity score dropped 12% after the prompt change"
  • Regression detection: Any change that hurts known-good cases shows up immediately
  • Cost/latency benchmarking: Quality isn't the only dimension — evals track all four: quality, cost, latency, error rate

Eval Architecture

Deterministic graders
Tool call correctness, output format, required fields — binary, no LLM
LLM-as-judge
Quality, reasoning, natural language outputs — rubric-driven, strong model
Replayability
Same test cases, same graders, run after every change
Task sampling
50-100 real examples from actual user projects
Setup time
Under 6 hours for rubric-driven system covering quality/cost/latency/error

LLM-as-Judge Rubric Design

💡 Key Principle

The rubric is the hard work. Vague criteria ("is this good?") produce unreliable judges. Specific criteria ("does the slide have exactly one core message, stated in the headline?") produce consistent, actionable scores.

  1. Write evaluation criteria as specific, binary-ish questions
  2. For each criterion, provide 2-3 examples of good vs bad
  3. Use a strong model (Opus-class) as the judge
  4. Run multiple judge passes and average — reduces variance
  5. Spot-check judge outputs periodically; judge hallucination is real

The Hill-Climbing Loop

Make a change → run evals → if score improves, keep; if not, revert. This is it. Simple, disciplined, effective. The power comes from doing it consistently rather than trusting intuition.

User Dissatisfaction as Eval Signal

💡 Insight

The most valuable eval inputs come from real user dissatisfaction. When a user says "this slide is wrong" or "this doesn't match what I meant," that's a concrete failure case. Log it, add it to your eval set, verify the fix doesn't regress it. Your eval suite becomes a curated catalog of real failure modes.

Actions

  1. Pick your top agent task and build an eval within 6 hours — quality + error rate minimum
  2. Add 50 real examples from user logs as eval inputs
  3. Write a detailed rubric for LLM-as-judge before configuring the judge
  4. Instrument your eval runner to track score delta per change, not just absolute score
  5. Log user negative feedback directly into the eval test set
