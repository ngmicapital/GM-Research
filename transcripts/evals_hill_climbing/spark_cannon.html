The talk builds a slide-generation agent live, adding increasingly sophisticated evals, and shows how each eval layer reveals failure modes that intuition would have missed.

Why Evals: The Vibes Problem

Agent development without evals produces "vibes-based" engineering: something feels worse after a change, or better, but you can't be sure. This has two failure modes:

  • False negatives: A change that actually improves performance feels neutral — you don't ship it
  • False positives: A change that hurts performance on the long tail feels good on the cases you tested manually — you ship a regression

Evals replace vibes with measurements. Not because vibes have no place — they're useful for generating hypotheses — but because vibes can't be acted on systematically.

📡 The Benchmarks Parallel

Model providers care intensely about benchmarks for the same reason: they need to know if a training change improved or regressed the model. Your application evals serve the same function for your system layer.

Anatomy of an Eval

An eval consists of: task definition (what the agent should do), test cases (inputs representing real usage), and grading logic (criteria for success). The grading logic is where most of the design work happens.

Deterministic Graders

For structured outputs with clear correctness criteria, use deterministic graders: exact match, regex, JSON schema validation, tool call inspection. These are fast, cheap, and perfectly consistent. Use them wherever you can.

LLM-as-Judge

For quality assessment, reasoning correctness, and natural language outputs, use an LLM as judge. The judge receives the task, the agent's output, and a detailed rubric, then scores the output on each rubric dimension.

💡 Rubric Quality is Everything

A vague rubric ("is this a good slide?") produces unreliable judges. A specific rubric ("does the slide headline state exactly one core message in under 10 words?") produces consistent, auditable scores. Write the rubric before configuring the judge. If you can't write specific criteria, you don't yet know what "good" means for your task.

⚠ Judge Hallucination

LLM judges hallucinate scores. Especially on nuanced criteria or when the output is long. Mitigations: run multiple judge passes and average, spot-check judge outputs on a sample weekly, use a stronger judge model than your agent model, give the judge specific examples of good vs bad for each criterion.

Slide Generation Agent Case Study

The demo agent generates presentation slides from user requirements. Failure modes are rich: wrong number of slides, incorrect content mapping to wrong slide, unclear headlines, visually unstructured content, missing key points, excessive content per slide.

Eval layers added progressively:

  1. Layer 1 — Structure: Does the output have the right number of slides? Are they in the right order? Deterministic.
  2. Layer 2 — Content mapping: Does each slide contain the content specified for that section? Deterministic + LLM check for paraphrase accuracy.
  3. Layer 3 — Headline quality: Is each headline a clear, specific statement (not a label)? LLM-as-judge with rubric.
  4. Layer 4 — Cognitive load: Does each slide have one core message? Is content density appropriate? LLM-as-judge.
  5. Layer 5 — User dissatisfaction inputs: Real failure cases from user feedback, added as test cases.

Each layer revealed failures the previous layers missed. Layer 1 found structural errors. Layer 3 found technically-correct but ineffective headlines. Layer 5 found the most important failure mode: cases where the agent produced valid output that didn't match user intent.

The Development Flywheel

The talk's central claim: evals done right become a self-reinforcing improvement loop. The mechanism:

  1. User reports dissatisfaction → add as test case → reveals failure pattern
  2. Failure pattern → prompt change / architecture change
  3. Change → run evals → score delta measured
  4. If improvement: ship, add to test suite, document what worked
  5. If regression: revert, understand why, try different approach
  6. Loop continues; each iteration adds to institutional knowledge of what works
💡 The 6-Hour Threshold

The speaker claims a rubric-driven eval system covering quality, cost, latency, and error rate can be set up in under 6 hours. This is a deliberate provocation: there's no valid excuse for not having evals. If your eval setup took longer than a day, something is wrong with the tooling or scope.

Multi-Dimensional Signals

Quality alone is an incomplete eval signal. A change that improves quality by 5% but doubles latency might be net negative for users. Track all four dimensions:

  • Quality: Rubric-scored outputs, task success rate
  • Cost: Token usage per task, API cost per successful outcome
  • Latency: Wall-clock time to first token, time to complete
  • Error rate: Tool call failures, malformed outputs, hard failures
🔁 Analog: A/B Testing

Multi-dimensional eval scoring is the agent equivalent of A/B test analysis. You don't just measure conversion rate — you measure conversion, revenue per user, and churn. Same principle: measure all the dimensions that matter before declaring a winner.

User Dissatisfaction as Ground Truth

The most valuable eval inputs are real user dissatisfaction signals. When a user says "this is wrong" or clicks a thumbs-down, that's a concrete, real-world failure case that your eval suite needs to cover.

Pattern for building this into your system:

  1. Log negative user feedback with the input that triggered it
  2. Periodically review logged failures, select representative cases
  3. Add as eval test cases — verify current system fails them
  4. Fix the failure, verify the fix
  5. Keep as regression test — never remove
💡 The Flywheel Compounds

As your eval suite grows with real failure cases, it becomes increasingly representative of the actual failure distribution. An eval suite with 500 real user failure cases is qualitatively different from one with 50 synthetic test cases — it surfaces the real edge cases, not the ones you imagined.

Implications

📡 Connection to Model Training

The reason model providers care so intensely about benchmarks and evals is identical to why you should: it's the only way to know if you're improving. Your application evals are to your system what MMLU and HumanEval are to foundation models.

⚠ Goodhart's Law Warning

When the eval score becomes the goal, it stops being a useful measure. Watch for prompt changes that game specific test cases rather than genuinely improving quality. Maintain a held-out evaluation set that you don't use during development — only run it at major milestones.
