Skills Beat MCP Alone: Supabase's Lessons from Writing the Hardest Document Since a Master's Thesis


Source: Pedro Rodrigues · AI Engineer Conference · ~18 min

Domain: AI Engineering / Developer Tools

Mode: Full


Speakers:

  • **Pedro Rodrigues** — AI Tooling Engineer, Supabase; Co-founder, Lisbon AI Week


    • Phase 1: Executive Summary


  • **Skills + MCP outperforms MCP alone on every model tested.** Supabase ran controlled evals across Claude (Opus 4.6, Sonnet 4.6) and OpenAI (GPT-5.4, GPT-5.4 mini) with three conditions — baseline, MCP only, MCP + skill. Skills won on test completeness score every time, across every model. (12:29–12:57)

  • **The context gap is the problem, not intelligence.** Agents using only MCP tools operated on stale training data and made critical security errors — specifically failing to set `SECURITY INVOKER = TRUE` on Postgres views over RLS-protected tables, silently exposing data. The skill prevented this by making the security checklist impossible to miss. (02:00–04:55)

  • **"If something can get skipped, it will be skipped."** Reference files in skill folders are frequently ignored by agents. Critical, non-negotiable instructions — especially security rules — must live in `SKILL.md` itself, not in referenced files. This is the single most important operational lesson from Supabase's experience. (07:42–09:09)

  • **Don't duplicate documentation; point to it.** Skills should direct agents to canonical up-to-date sources (docs, APIs), not reproduce them. The goal is guidance, not encyclopaedia. Combined with exposing docs via SSH filesystem so agents can navigate them like a Unix file tree. (05:56–07:32)

  • **Be opinionated in your skill.** You know your product's optimal workflows better than any agent. Encode them explicitly. Supabase's schema management workflow — DDL freely on dev → advisor → migration — is in the skill because agents without it create migration files on every schema change, polluting version history. (09:14–10:58)

  • **Start minimal, iterate.** Every model vendor says this. Rodrigues confirms it from experience: overloading a skill early is counterproductive. Build the minimum viable skill, measure via evals, expand. (13:41–13:56)


    • Phase 2: Thematic Deep Dives


    🔑 The Core Problem — Stale Knowledge + No Guardrails


    *"We noticed that they would usually miss some security pitfalls… and they're very lazy and stubborn to admit that they don't know and do need to find fresh information."* (02:08)

    Agents suffer from three failure modes on complex products like Supabase:


  • **Stale training data** — they know a version of the product from pre-training, which may be months or years old
  • **Security blindspots** — they default to the "obvious" implementation without knowing product-specific requirements (e.g., `SECURITY INVOKER` on views)
  • **Tool laziness** — agents resist web searches and reference file reads because these are expensive (token-wise) compared to defaulting to weights

    • The Postgres view vulnerability Rodrigues demonstrates is a sharp example: creating a SQL view over an RLS-protected table without SECURITY INVOKER = TRUE causes the view to bypass row-level security entirely, silently exposing all user data. An agent without skill context made this mistake; one with the skill did not.


    🔍 **Source Verified:**
    ✅ The `SECURITY INVOKER` issue is a real and documented Postgres behavior. Per PostgreSQL documentation, views execute with the privileges of the **definer** (usually the superuser) by default. `SECURITY INVOKER = TRUE` (added in PostgreSQL 15) makes the view execute with the caller's privileges, respecting RLS. This is a genuine security risk and Rodrigues' framing is accurate.

    🎯 **Against Consensus:** The standard AI community framing is "give the model more context and it will perform better." Rodrigues' finding is more specific: *where* you put the context matters as much as *what* you put there. Context in `SKILL.md` body is reliably ingested; context in reference files is frequently skipped.


    📂 Anatomy of a Skill — What Goes Where


    Skills are folders with:

    
skill-name/
├── SKILL.md          ← Main file: name, description (front matter), instructions
├── scripts/          ← Executable helpers agents can run
└── references/       ← Additional reference files (WARNING: often skipped)

    Front matter (name + description) is how agents decide whether to load the skill. This is the trigger mechanism. A poorly written description means the skill never fires.


    Rodrigues' hierarchy of what gets read:

  • `SKILL.md` body — always read when skill is loaded ✅
  • First reference file — sometimes loaded if explicitly needed ⚠️
  • Second reference file — rarely loaded 🔴
  • Third/fourth reference files — essentially never 🚫

    • 💡 **Key Insight:** The reference file problem is a form of the lazy loading anti-pattern. Agents optimise for token efficiency; every file read costs tokens and time. The practical implication is that any instruction you need the agent to *always* follow must be in the main skill body. Reference files are for "look this up if you're implementing X specifically" content.


    🧪 How Supabase Tested the Skill — Running Evals on Markdown


    *"We're living in very interesting times where we can now test documents. This would be completely bonkers to think about years ago. I've basically been testing a markdown file."* (11:00)

    Supabase used Braintrust to run evals:

  • **6 scenarios** covering representative Supabase tasks
  • **4 agents**: Claude Opus 4.6, Claude Sonnet 4.6, GPT-5.4, GPT-5.4 mini
  • **3 conditions**: baseline (no MCP, no skill), MCP only, MCP + skill
  • **Scoring**: completeness score (0–4 graded)

    • Result: Skills + MCP outperformed on every model. The improvement was not model-specific — it was a universal signal that context/guidance is the binding constraint, not raw model intelligence.


    🌐 **Consensus Check:** Eval frameworks for agent behavior (Braintrust, Langsmith, METR) are an emerging but rapidly solidifying practice. The methodology Rodrigues describes — testing documentation quality through agent performance — represents the state of the art in agentic quality assurance as of 2025.


    🗂️ The SSH Docs Experiment — File System as Documentation Interface


    Supabase is exposing its documentation through SSH, structured as a filesystem. The hypothesis: agents are deeply familiar with navigating filesystems using Linux tools (ls, find, cat, grep). By exposing docs in that interface rather than as web pages, agents can navigate documentation the way they navigate code.


    This is experimental but philosophically aligned with the broader Karpathy-era insight that agents work best when the environment matches their training distribution. Agents trained on billions of lines of bash commands can navigate a Unix tree more naturally than a React SPA.


    🔗 **Connection:** SSH docs → agent-native infrastructure. This maps directly to Karpathy's complaint (Video 3) that documentation is still written for humans, not agents. Supabase is directly attacking that problem.


    🏗️ The Opinionated Workflow — Schema Management as Case Study


    Supabase's encoded schema workflow in the skill:


    
1. Run DDL freely on development/staging database
   (change schema without migration files)
2. When satisfied, run the Supabase Advisor
   (catches security and performance issues)
3. Fix any advisor-flagged issues
4. Only THEN create the migration file

    Without this workflow encoded, agents create a migration file after every schema change, producing a polluted version history. The skill enforces the correct discipline.


    💡 **Key Insight:** This is the core value proposition of opinionated skills — they encode *workflow* knowledge, not just *factual* knowledge. An agent can know what RLS is without knowing that Supabase expects you to run the advisor before migrating. The latter is tribal knowledge that lives in your head and dies when you leave the team.


    📦 The Distribution Problem — Skills Need a Package Manager


    When asked about internal skill distribution, Rodrigues acknowledged it remains unsolved:


    Current approaches:

  • Packaging skills in repos (`.claude/`, `.cursor/` folders)
  • Using `skills` package to fetch from open-source repos
  • Vercel's skills package
  • Anthropic's plugins (bundles MCP + skills)

    • The problem: unlike npm for Node or pip for Python, there is no universal, cross-model, cross-IDE skill registry. Every platform is trying to claim the standard. This is a distribution layer problem that predates the technology being mature enough for a solution.


    ⚡ **Tension:** Rodrigues calls this an "open problem" and is visibly unsure during the Q&A. Yet Anthropic's plugin system (featured in Video 4) appears to be a direct attempt to solve exactly this — bundling MCP servers + skills together. The ecosystem is fragmenting and consolidating simultaneously.


    Phase 3: Three Principles Card


    📋 Principle 1: Don't Duplicate Documentation

    **What It Means:** Point agents to your canonical source of truth. Don't try to reproduce your docs inside the skill — they'll be stale immediately.
    **Implementation:** Add instructions to the skill that tell agents *where and how* to find fresh documentation, and be persistent about it: the agent will default to training data unless you explicitly and firmly instruct otherwise.

    📋 Principle 2: If Something Can Be Skipped, It Will Be Skipped

    **What It Means:** Reference files are often ignored. Critical non-negotiable instructions must live in `SKILL.md` body.
    **Implementation:** The security checklist at Supabase (RLS, SECURITY INVOKER, etc.) was moved from a reference file to the main skill body after agents routinely missed it. The move to the main body made it impossible to skip.

    📋 Principle 3: Be Opinionated

    **What It Means:** You know your product's optimal workflows. Encode them. Don't let the agent guess.
    **Implementation:** Supabase's schema workflow (DDL → advisor → migration) is explicit and step-by-step in the skill. Without this, agents improvise suboptimal paths.

    • Phase 5: Protocol Cheat Sheet


    📋 **Skill Writing Protocol:**
    - Critical security rules → `SKILL.md` body (never reference files)
    - Doc links → always include "where to find fresh docs" instructions
    - Be stubborn: explicitly tell the agent to go look things up, repeatedly
    - Encode your canonical workflow step-by-step
    - Start minimal, test via evals, iterate
    - Reference files = "nice to have, usually skipped" — treat accordingly
    - Eval framework: Braintrust recommended; test like you're testing code
